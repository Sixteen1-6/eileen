# Owner direction

What the owner has asked Eileen to be, in dated entries. Design documents (BUILD.md, ARCHITECTURE.md, ROADMAP.md) must satisfy every entry here. When an entry conflicts with an older decision in DECISIONS.md, the newer entry wins and a decision record says so.

## 2026-10-11

- **Name.** The product is Eileen. That is final.
- **Always listening.** You talk to the computer any time the mic is not muted. No wake word is required. Mute is one keypress or one click away.
- **Anything a human can do on a computer.** Open and drive any app, go to a specific video, edit in pro apps. Benchmark requests:
  - "Open the video editor, go to 15:30 and make the face of the girl on the right less blurry", and it actually does it in DaVinci Resolve.
  - "Open Photoshop, open the image where I was editing the girl at the beach, and make her face less blurry."
  - "Launch three agents to do X", and they run in parallel.
  - Writing code by speaking.
- **Subscriptions, not API keys.** Models run through each vendor's official, signed-in tool on the owner's existing plans (Claude Code for Claude, Codex for OpenAI). Every model goes to its own harness and to what it is best at. Workers are named by route: Claude, Codex, Grok, DeepSeek. Local models (Ollama and similar) are optional support, never required. Small local speech models are fine.
- **Fast, and in Rust.** The always-on runtime is Rust. The code is spotless: formatted, linted with warnings as errors, tested, and license-checked on every pull request.
- **Open source, on GitHub.** Anyone can download it. Work is pushed as it happens, with tests.
- **Not already done.** Check the prior art honestly and build something clearly better than it.

## 2026-10-20

- **API keys.** No Gemini API key. Gemini is out until a subscription route exists that Google permits for tools like Eileen. A DeepSeek API key is acceptable for now; it is the only key.
- **The feel.** Eileen should feel like talking to a brilliant assistant in the room while you work on something hard. Concretely:
  - It understands natural, half-finished speech and context ("make that bigger", "no, the other one", "go back to what we tried an hour ago").
  - It knows when you are talking to it and when you are not, and when you have finished a thought versus paused mid-sentence.
  - You can interrupt it at any moment and it stops at once, then picks up from what you actually heard.
  - It talks while it works: short, useful narration of what it is doing and what it found, never filler, never a wall of text read aloud.
  - It works on several things at once and keeps you oriented ("the render is at 60 percent; the test agent found two failures").
  - It thinks with you on hard problems, not only executes commands: it can explore, simulate, compare options and explain.
  - A visual layer (a heads-up display or overlay on the screen) shows what it is listening to, doing and watching, since there are no holograms.
- **Signing in.** The owner signs in to each vendor CLI themselves. Eileen never runs a login flow and never reads vendor credential files.
- **Claude is the default.** For now the brain and every worker route to Claude on the owner's plan. Codex is added later, once the owner installs and signs in to the Codex CLI; the routing design keeps a slot for it and for Grok and DeepSeek, but v0.1 must work end to end with Claude alone.
- **Public.** The repository is public as of 2026-10-20.
- **Eileen learns from every request. This is a main point of the product.** When someone asks for something hard and a worker finds a way to do it, that way is captured and built in, so the next time the same kind of request comes in it is faster, cheaper and more reliable, and eventually needs no model at all. Eileen keeps learning from how the user works (their apps, files, habits, phrasing and corrections) and gets better over time. Concretely, v0.1 must include:
  - recording what each job did (the request, what was on screen, every tool call, the result, and whether the user was happy, corrected it or undid it);
  - turning a successful job into a reusable, named skill that future workers load automatically;
  - matching new requests to known skills, and replaying a well-proven skill directly, checking each step and falling back to a worker the moment a check fails;
  - repairing a skill when it breaks, with its history kept so a bad change can be rolled back;
  - letting the user ask what Eileen has learned, correct it, or tell it to forget something;
  - keeping all of this on the user's PC, private by default, with any sharing of skills strictly opt-in and stripped of personal data;
  - never letting a learned skill skip a confirmation or raise a permission, and never turning text seen on screen into a skill without the user's say-so.
- **Connected fully to the computer, then to everything around the user.** v0.1 is the whole PC: every app, file, window, setting Eileen is allowed to touch, and the browser. After that Eileen reaches outward: the phone (messages, notifications, voice from anywhere), the home (lights, speakers, TV, thermostat and other devices, preferably through an open, local hub such as Home Assistant and standards such as Matter), other computers and devices the user owns on their own network, and earbuds or other microphones as ways to talk to it. The architecture must treat each of these as a pluggable connector with the same permission tiers, learning loop and job model as the PC, so adding one later is a new connector, not a redesign. Privacy rules get stricter as the reach grows: anything that senses the room (cameras, always-on mics beyond the PC) is opt-in per device and processed locally.
- **Windows first, not Windows only.** The owner runs Windows, so v0.1 targets Windows 11 and is tested there. Linux support follows soon (macOS later). Everything that touches the operating system (desktop grounding, UI automation, input, screenshots, audio devices, media control, app hooks, credentials storage, the HUD window) sits behind platform traits in its own crate, so porting means writing a new platform crate (for Linux: AT-SPI accessibility, PipeWire audio, Wayland or X11 input and capture, D-Bus MPRIS for media, Secret Service for secrets), not reworking the core. The platform-neutral crates (brain, jobs, event bus, router, learning loop, workers, config) must build and pass their tests on Linux from day one, checked in CI on ubuntu-latest, so they stay portable while Windows is the only full target.
- **Dictation better than the paid tools.** Eileen includes a dictation mode as good as or better than the commercial voice-typing apps: speak and clean, punctuated text lands in whatever field has focus, in any app, with filler words and false starts removed and the user's vocabulary learned over time. Built on the best open-source work available (verify the current leaders), local and free.
- **Any voice.** Eileen's speaking voice is configurable. Kokoro stays the fast default; Chatterbox (or something better, if the research finds one that runs well on this PC) lets the user pick or clone a voice. Cloning uses only a voice the user has the right to use (their own, or one with consent).
- **Any voice must be easy, including a friend's.** One step: "Eileen, learn a new voice", then either the person speaks to the mic for about 30 seconds or the user drops in a clip. The flow has the voice's owner read a short consent sentence in their own voice, which is checked and stored with the voice profile, on the PC only. Voices are named profiles ("use Sam's voice", "back to normal"), can be assigned per purpose (for example a different voice for announcements), and can be deleted by voice. If the cloning model is too slow for live conversation on the PC, Eileen says so and uses the cloned voice where latency matters less (announcements, summaries, read-alouds) while keeping the conversation instant.
- **Best possible answer at conversational speed.** A thinking model that researches gives far better answers than a fast one, even for everyday questions like "what's the best place to eat near me". Eileen gets both:
  - Two speeds at once: the fast brain answers within about a second with something useful (never filler), while a deep worker (the strongest model, thinking on, web research) runs in parallel; Eileen speaks the better answer when it lands, and the user can keep talking or interrupt throughout.
  - Depth matched to the question: instant (no model), quick (fast model), considered (mid model, light thinking), deep (strongest model, thinking and research). The brain picks; "quick answer" or "think hard about this" overrides.
  - Research fans out: several searches run in parallel (reviews, hours, distance, prices) and one model combines them, so deep answers take tens of seconds, not minutes.
  - Context makes it right: location (opt-in, local), time, what the user likes and has done before (from the learning loop's user model), and what they are doing right now.
  - Short when spoken, rich on screen: two sentences aloud, the full list with links, reasons and actions on the HUD.
  - Faster every time: the learning loop remembers which sources gave the best answers for each kind of question, slow-changing results are cached with an expiry, and the user's follow-ups ("closer", "I loved that place") are kept.
  - Optional anticipation (off by default, because it spends plan limits): looking things up before the user asks.
- **Engineered extremely well from the ground up.** Learn from the best-run open-source repositories and use the best techniques. Concretely:
  - Work is pushed continuously: every finished piece lands on GitHub as it is done, on its own branch and pull request, and merges only with green checks.
  - Testing in layers: unit, property and snapshot tests in Rust on every PR; integration tests across crates; deterministic simulation of the core (jobs, event bus, scheduling, barge-in timing) so concurrency bugs are reproducible from a seed; scripted end-to-end scenarios on a real Windows desktop with recorded audio instead of a live mic; the owner's benchmark requests as timed scenarios; fuzzing of every parser that reads untrusted input; long soak tests for an always-on process (memory, handles, CPU while idle).
  - Easy to configure and to understand: for every part of the code, what it owns, its invariants, how to test it and what not to touch must be written down where people and AI agents (Claude, Codex and others) reliably find it, plus an ARCHITECTURE.md map, decision records, and user configuration in readable files with comments. The form is not fixed in advance (a CLAUDE.md in every folder is only one option): use whatever the best-run repositories show works best, for example one shared AGENTS.md that Claude also reads, guidance files only where a folder has genuinely different rules, and crate documentation inside the code itself. Decided by the engineering-practice research, recorded as a decision.
  - The conventions are enforced by CI, not just written down. Whatever ways of working we adopt from the best repos (documentation structure, contribution flow, code style, how code is updated and managed) get an automated check that fails the pull request when broken. For example: every crate has its guidance in the chosen form with the required content, and ARCHITECTURE.md lists exactly the crates that exist; Markdown is linted, links resolve and spelling is checked; docs follow the house style (no em dashes, the product only ever called Eileen, no "Claude Code <something>" branding, no film or trademark names); commit messages and PR descriptions follow the agreed format and the PR template is filled in; the generated code map is current; every unsafe block has a SAFETY comment; public items are documented; decision records follow their template; new dependencies pass the license and advisory policy. The checks are fast, run on every PR, run the same way locally with one command, and the list of checks is itself documented so contributors (people and AI agents) know the rules before CI tells them.
  - Traceable and debuggable: every request gets an ID that follows it through voice, brain, job, worker, tool call and result; structured logs and spans; a flight recorder of the last minutes that can be dumped when something goes wrong; replay of a recorded session to reproduce a bug; a generated code map (crate and module graph, call graph where useful) kept current by CI, so a bug can be traced from symptom to code quickly, by people and by AI agents.
- **Use Claude's official extension points to make the Claude app better with Eileen.** Claude now supports mods (changes to its interface and behaviour such as panes, panels, status lines, toasts, slash commands and hooks), plus plugins, skills and hooks in Claude Code. Where these make Eileen better, use them: for example Eileen's jobs and status inside the Claude app, Claude sessions reporting progress and approval requests to Eileen, Eileen's learned skills available to every Claude session. Only through the supported mechanisms, never by patching or replacing the app, so the owner keeps getting the latest Claude updates.
- **Customise anything by just saying it.** The owner wants changes like these to be one sentence away: "Hey Eileen, I want to call you Nova now" renames the assistant (the name it answers to, the name cue in addressee detection, the recognition hint for speech-to-text, how it refers to itself); "use Sam's voice"; "talk less", "be funnier", "always answer in one sentence"; "speak faster"; "stop announcing progress on renders"; "put the HUD bottom left and make it smaller"; "always let Claude move windows without asking me"; "use the strongest model for anything about code"; "change the mute key to F8". Rules:
  - Every setting a person might want is reachable by voice and in the HUD, and lands in readable, commented config files the user can also edit by hand.
  - Eileen confirms a change in one short sentence, and "undo that" or "go back to how it was" reverts it; settings are versioned locally so any earlier state can be restored.
  - When a choice could misfire (a new name that sounds like a common word or someone in the house, a mute key already used by another app), Eileen tests it first (for example says the new name and checks it recognises it reliably) and warns before applying.
  - Settings can be saved as profiles ("work mode", "editing mode") and switched by voice, and exported to share.
  - The product and repository are still called Eileen; this is the user's own assistant's name, voice and personality.
  - Safety settings follow the permission tiers: a user can relax confirmation for reversible things, but nothing a setting does can let Eileen enter credentials, make payments or skip confirmation for tier-2 actions without an explicit, logged decision by the user.
- **Voice cloning engine and watermarks (decided 2026-10-20).** Use whichever permissively licensed cloner is best on the PC; per the dictation-and-voices research that is Kyutai Pocket TTS (MIT code, CC-BY-4.0 weights, credited in the about screen and NOTICE file), streaming through Eileen's own sherpa-onnx path, with Kokoro as the default voice. Chatterbox is an optional extra for pre-rendered expressive speech only. No watermark by default on any engine, Chatterbox included (its Perth watermark is turned off); watermarking is an opt-in setting for users who want it on saved or exported audio. The consent enrollment for cloned voices stays, since it protects the people whose voices are cloned.
- **AI-native at the root: intent, not commands.** Users never have to learn what to say. Any phrasing, in any language, typed or spoken, half-finished or vague, maps to the right action, because resolving intent is the job AI models are good at. The resolver is layered so it stays instant where it can:
  1. a deterministic fast path for exact and learned phrasings (no model, instant);
  2. a local semantic matcher in Rust (a small on-device embedding or classification model) that maps paraphrases to known actions and skills in milliseconds;
  3. the brain for everything else, with the live context (focused app, its UI tree, selection, jobs, user model);
  4. when no capability exists yet, a worker figures it out and the learning loop turns the result into a skill, which then feeds layers 1 and 2.
  Unclear requests get one short clarifying question, never an error. "What can you do here?" is answered by introspection (the tools registered, the focused app's controls and hooks, the learned skills that apply), not from a static list. The HUD suggestions are a bonus built on the same introspection, not the fix.
- **Use AI wherever it makes the engineering better, not only in the product.** Where a model makes a part of the system more robust, faster to build or easier to fix, use it, with deterministic checks around it. For example:
  - self-healing UI automation: when a control's automation ID or position changes after an app update, re-find it by its description and update the skill;
  - natural-language settings and config edits (already in "customise anything");
  - bug triage: the flight recorder and replay feed a worker that explains what went wrong and points at the code, from the code map;
  - test generation: successful and failed trajectories become regression scenarios automatically;
  - documentation upkeep: a check that flags when code changed but its guidance did not, with a drafted update;
  - code review on pull requests by a Claude worker in addition to the deterministic CI gates, set up by the owner on their own account;
  - error messages that explain themselves in plain language and offer the fix.
  Deterministic code stays the default where it is exact and cheap; AI fills the places where rules are brittle.
- **Real use becomes automated tests (community scenario corpus).** The owner's friends will install Eileen on their own PCs and test it. Everything they and the owner try should feed the test suite, so tests keep growing from real use instead of only from what developers think of:
  - **Capture.** "Eileen, save that as a test" (or a HUD button, or `eileen scenario save`) turns the last request into a scenario file: what was said (as text; the person's real voice only if they explicitly allow it, otherwise regenerated with a stock voice), the starting state (apps open, fixture files), every step Eileen took, and the expected outcome as checkable assertions (window on monitor 2, text inserted, file changed, Resolve playhead at 15:30). Failures are saved the same way, with the flight recorder attached.
  - **Generic and private.** Before anything leaves the PC it is generalised and redacted: names, emails, paths, account details and screen text are replaced with placeholders, screenshots are off by default, and the contributor sees exactly what will be shared and approves it.
  - **Sharing.** An approved scenario is submitted from the contributor's own GitHub account as a pull request or an issue using a scenario template. CI validates it against the scenario schema and replays it in simulation (recorded tool inputs and outputs, no real desktop needed) on every PR, so a shared scenario is a permanent regression test.
  - **A test fleet of real PCs.** Contributors can opt in to run the real-desktop scenario suite on their own machine (`eileen test --fleet`, nightly or on demand) and upload a results file (pass, fail, timing, Windows build, monitors, DPI, app versions, no personal data). Different machines, apps, languages and screen setups catch what one PC never would.
  - **Learning from it.** Failures are clustered and triaged by a worker using the replay and the code map; a fixed bug always leaves its scenario behind as a regression test; flaky scenarios are tracked and fixed, not ignored; skills from the learning loop are checked across many machines before they are promoted for sharing.
  - **Visible.** The repo keeps a readable catalogue of scenarios (what people actually ask Eileen to do, grouped by app), which doubles as examples for new users, and a coverage view of which apps and requests are tested on how many machines.
  - **A testers' guide.** A short TESTING.md tells friends how to install, what to try, how to save and share a scenario, and how to run the fleet suite.

## Proposed 2026-10-20 (by the assistant, not yet confirmed by the owner)

Ideas to make Eileen genuinely easier to use and more trusted. The architect adopts for v0.1 the ones that are cheap and high value and schedules the rest; the owner can strike any of them.

- **Undo for everything.** Every action Eileen takes is journaled with how to reverse it. "Eileen, undo that" reverses the last action or the last job's changes (window moves, typed text, file edits through git, app changes where the app supports undo). People let an assistant act only when they can take it back.
- **Visible intent.** Before a click or keystroke on the user's screen, the HUD highlights the target for a moment and names it, so "no, the other one" works mid-action. A "show me first" mode previews a whole plan before anything runs.
- **Teach by showing.** "Eileen, watch me do this": the user does a task once while Eileen records it through its own hooks, then it becomes a skill in the learning loop. Programming by demonstration, with the same consent and safety rules.
- **Discoverability.** Voice assistants fail when people do not know what to say. The HUD shows two or three context-aware suggestions ("in Resolve you can say: jump to the next marker"), a first-run spoken tour, and "what can you do here?" answers for the app in focus.
- **Focus awareness.** Eileen stays quiet during calls, presentations, full-screen games and recording (it can tell when the mic is in use by another app or a window is full screen), holds announcements, and summarises them afterwards.
- **Plan-limit awareness.** Eileen tracks how much of the Claude plan it has used, routes small things to cheaper models, warns before a big parallel job would hit the limit, and never silently burns the user's allowance.
- **Accessibility as a first-class goal.** Hands-free control of the whole PC is life-changing for people with repetitive strain, motor impairments or low vision. Design for them from the start: full keyboard-free operation, compatibility with screen readers, adjustable speech rate, and no task that requires a mouse.
- **Memory you can ask about.** "What was that page about GPU pricing I had open yesterday?" answered from the local episodic desktop ledger, private and searchable, with an off-the-record mode that records nothing.
- **Routines.** "Every weekday at nine, summarise my inbox and start the nightly build report": scheduled jobs that use the same workers, skills and permission tiers.
- **Shared skills, opt-in.** People who use Eileen can share generic skills (stripped of personal data, signed, reviewed, untrusted until verified locally), so every new user starts with what thousands of others have already taught it. This is how a personal assistant gets better for everyone, not only for one person.
- **Languages.** The speech models already cover many languages; let the user talk to Eileen in their language and switch mid-conversation.
- **One-step install.** A single installer (winget and a signed MSI) that checks for the Claude CLI, walks the user through signing in themselves, downloads the speech models, and ends with Eileen saying hello.
