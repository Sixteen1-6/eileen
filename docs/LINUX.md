# Eileen on Linux: the plan, Ubuntu first

A proposal, written 2026-10-21 after the owner asked that Linux be supported in the plan. It is for the owner, who decides what it changes in [BUILD.md](BUILD.md), and for whoever builds the Linux backends. It changes nothing in the Windows design. Linux implements the same platform traits of BUILD.md section 3.4, in `-linux` crates that mirror the `-win` crates, and the neutral crates stay as they are.

Sources are linked where they are used. Crate versions were read from crates.io on 2026-10-21; "eligible" means the newest release at least 14 days old that day (BUILD.md section 4.1's cooling-off rule). Statements marked [inferred] are reasoning that a later measurement must confirm.

## 1. Summary

- **What already holds.** Every platform-neutral crate builds and passes its tests on Linux, which CI's `logic-linux` job checks on every pull request (BUILD.md section 4.6). On Ubuntu 24.04 the full Linux lane passed on `main` at daf8e13 (fmt, cargo-deny, cargo-machete, clippy with warnings denied, 165 of 165 tests, doc tests, docs), and `logic-linux` passed 948 of 948 tests on `main` at 5a4b11b (CI run 40238334151) and 1057 of 1057, with the 4 desktop-lane session tests skipped, at a84c198 (CI run 40414356056).
- **What Linux needs.** Implementations of the rest of the section 3.4 traits (`main` serves `ShellHost`, `SystemMemory`, `MediaSessions`, `Apps`, `RecentSources` and `AudioEndpoints`, the last three in part, and `MachineIdentity` through `eileen_platform::machine::FileMachineIdentity`; section 4), the rest of the Linux process model behind `eileen-supervisor` (`main` has each child's session, process group and parent-death signal; the cgroup scope and `user_launch` are still to come, section 5), Linux paths in the data directory and the path classes, and test lanes that exercise real Linux desktop services, of which the nightly Linux desktop lane runs since #83 (section 6).
- **The reference desktop.** Ubuntu 26.04 LTS with GNOME on Wayland, which is the only GNOME session it ships. Ubuntu 24.04 LTS (GNOME 46) is supported where its desktop allows. KDE Plasma and wlroots compositors come second.
- **How it is built.** A new work package, WP10 (section 8), runs on a Linux machine of its own. It uses none of the owner PC's build slots and lands in four phases:
  - L0: memory, machine facts, identity, and the Linux lane;
  - L1: the D-Bus services;
  - L2: audio, accessibility, input and the HUD, ending in slice S1 on Linux;
  - L3: packaging and the Linux fleet.
- **What Linux cannot match without consent.** Wayland keeps clients from reading other windows' positions, injecting input or capturing the screen on their own. Eileen asks once through the desktop portals, and a few Windows behaviours (background input to a named window, a click-through overlay on GNOME) degrade honestly (section 3).

## 2. Where Linux stands in the plan today

- **The owner direction.** "Windows first, not Windows only": everything that touches the OS sits behind platform traits, and the neutral crates build and test on Linux from day one ([OWNER-DIRECTION.md](OWNER-DIRECTION.md), 2026-10-20; decision D38).
- **The roadmap.** It lists Linux as a v0.2 target, built as "`-linux` platform crates: AT-SPI, PipeWire, Wayland or X11, MPRIS, Secret Service" ([ROADMAP.md](ROADMAP.md)). BUILD.md section 3.4 marks the traits "Linux later": `MediaSessions` on MPRIS, `SecretStore` on Secret Service, `MachineProbe` on "/proc, sysfs and udev", and `AppHost` per app.
- **Already Linux-aware in the design.**
  - On Linux the speech pipe is a Unix socket under `$XDG_RUNTIME_DIR/eileen/`, mode 0700, and the speech process checks its server with `SO_PEERCRED` (BUILD.md 3.3.7, section 5 below).
  - The fleet's machine hash reads `/etc/machine-id`, then `/var/lib/dbus/machine-id` (owner answer 6; `eileen_platform::machine::FileMachineIdentity`).
  - `ConnectorManifest.platforms` and `MachineFacts.os` carry `Linux` (3.3.12, 3.3.17).
  - Native libraries appear only under Windows target tables, so the Linux lane never links them (4.1).

| Audio | PipeWire with its PulseAudio server [inferred: Ubuntu's default since 22.10] | The same |
| CI | GitHub moves `ubuntu-latest` to 26.04 between 2026-10-19 and 2026-11-19 ([GitHub changelog](https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration)) | `ubuntu-24.04` stays available |

What GNOME on Wayland means for each part of Eileen:

- **Reading the desktop.** AT-SPI2, the accessibility bus over D-Bus, gives the application, window and element trees, states (focused, active, editable), actions and text, much as UI Automation does. Wayland gives a client no global window coordinates and GNOME exposes no protocol for listing other clients' windows, so `DesktopState` on Linux carries window-relative element boxes. Monitor geometry comes from the compositor's own D-Bus interface or `wl_output`, and the window list comes from AT-SPI's frames [inferred; L2 measures it].
- **Input and capture.** No client may inject input or read the screen without the user's consent. The XDG RemoteDesktop portal's `ConnectToEIS` hands Eileen an EIS socket for libei, after which input goes to the compositor directly ([libei portal integration](https://planet.gnome.org/page4.html)). The ScreenCast portal hands Eileen a PipeWire stream. Each asks once, and a restore token keeps the grant. The Windows rule "background input to a named window" has no Linux equivalent: input goes to the focused surface, so on Linux every keyboard and pointer action is a foreground action and takes the input lock and a lease (BUILD.md 2.6).
- **Global shortcuts.**
  - On 26.04, the mute key and the dictation key come through the GlobalShortcuts portal. On GNOME its `Activated` and `Deactivated` signals are not a key's state. `Activated` comes again with each auto-repeat while the key is held, since mutter runs the shortcut again and xdg-desktop-portal-gnome keeps no pressed state. `Deactivated` comes only when the key is let go while its chord's modifiers are still down, since mutter looks a release up with the modifiers it carries. So a dictation key bound to a chord can miss its release, and hold-to-talk cannot rely on it (mutter's `src/core/keybindings.c` and xdg-desktop-portal-gnome's `globalshortcuts.c`, read on 2026-10-25 for #93). Eileen counts a press only when the shortcut was up (#107). A press names no device: the portal drops it, and input injected through libei fires the shortcut too, so on Linux the approve, deny and unmute hotkeys cannot be checked for a keyboard device as Raw Input checks them on Windows. Until the owner decides how BUILD.md sections 2.5 and 2.9 apply on Linux, a Linux composition root must not map a press, or a tray choice, which any program on the session bus can send, to `Approve`, `Deny` or an unmuting `SetMute` or `ToggleMute` (`LinuxShellEvent`'s doc).
  - The portal needs the app's ID. Eileen's client registers it with the host registry (`org.freedesktop.host.portal.Registry`, xdg-desktop-portal 1.19.4 and later) before it opens a session, and the registry takes only the basename of an installed desktop file. xdg-desktop-portal 1.21.0 and later refuse a session to an app without an ID, and GNOME Settings discards a bind from one, so Eileen's desktop file must be installed (L3's packages install it). GNOME keeps the trigger the user chose for each shortcut ID, and asks again only for shortcuts it has not stored.
  - GNOME answers a bind dialog the user dismissed with 2, not 1. Closing the bind's request does not dismiss GNOME's dialog: an accept that comes later is stored but binds nothing until the next bind of those shortcuts, which GNOME answers without a dialog.
  - On 24.04 there is no portal backend. Eileen offers to add GNOME custom keyboard shortcuts that run `eileen ctl mute` and `eileen ctl dictate --toggle`, so dictation there is toggle, not hold [inferred].
  - Reading the keyboard directly (evdev) needs the `input` group, which Eileen never asks for.
- **The HUD.** GNOME's compositor implements no wlr-layer-shell ([fuzzel's GNOME fallback discussion](https://zff.dev/dnkl/fuzzel/pulls/758)), so a client cannot place an always-on-top, click-through overlay on GNOME. The options, in order:
  1. A small GNOME Shell extension that draws the HUD from `HudState` over D-Bus. It is JavaScript, so it needs the owner's decision.
  2. wlr-layer-shell on KDE Plasma and wlroots compositors.
  3. A normal window plus notifications.

  L2 measures and picks.
- **Tray, notifications, secrets, media, power and lock state** are D-Bus services every Ubuntu desktop runs:
  - the tray: StatusNotifierItem, which Ubuntu's GNOME shows through its AppIndicator extension [inferred: shipped and enabled by default; verify on 26.04];
  - notifications: `org.freedesktop.Notifications`;
  - secrets: the Secret Service (GNOME Keyring);
  - media: MPRIS, which browsers and media players expose;
  - power: UPower and power-profiles-daemon (its `power-saver` profile is the battery-saver fact);
  - lock state: logind's session `LockedHint`, which GNOME Shell and KDE Plasma's locker set and swaylock does not.

## 4. Each trait on Linux

The traits are BUILD.md section 3.4's, with the signatures in `eileen-platform`. Each Linux crate mirrors a Windows one:

| Linux crate | Process | Mirrors |
|---|---|---|
| `eileen-shell-linux` | core | `eileen-shell-win` |
| `eileen-audio-linux` | core and speech | `eileen-audio-win` |
| `eileen-desktop-linux` | desktop | `eileen-desktop-win` |
| `eileen-apps-linux` | apps | `eileen-apps-win` |
| `eileen-hud-linux` | HUD | `eileen-hud-win` |

Every one of them is gated with `#![cfg(target_os = "linux")]`, so on Windows it compiles to an empty library, as the `-win` crates do on Linux. `eileen-shell-linux` and `eileen-apps-linux` are on `main`, and so, since BUILD.md section 3.1 gained their rows (#78 and #80), are `eileen-desktop-linux`, with its AT-SPI2 client and no trait served yet (#87), and `eileen-audio-linux`, with `register_audio_thread` (#90). Neither is wired into its process yet: `eileen-desktop`'s manifest has no target table, and `eileen-audio`'s and `eileen-speech`'s have only Windows ones. `eileen-hud-linux` is planned.

Their D-Bus clients share one more crate, `eileen-dbus-linux`, which has no Windows counterpart. It holds `DbusError`, its mappings and its `From` into `PlatformError`, the session and system buses with a method timeout, name owners and their `NameOwnerChanged` signals, the signal-stream helpers `subscribe` and `drain`, the portal `Request` client, whose `answer` gives the portal's results, and `close_request`, which closes a request and waits for the answer, the `Bridge` below, and, for tests, a private bus and a silent one behind its `private-bus` feature. No client writes its own.

The traits are synchronous and the clients are async, so the `Bridge` (#62) runs them: one named thread, `eileen-dbus`, with a current-thread tokio runtime. A trait call posts a job there and waits at most its deadline; past it, the call answers `DeadlineExceeded` and the job is cancelled. A job reaches the buses through `Buses`, which keeps the shared session and system connections and connects again once one closes, or opens a session connection of the job's own. Jobs answer plain data, never a connection, proxy or stream, and leave the runtime's two blocking threads to zbus, which connects a Unix socket on them, so a job that touches files does so on a thread of its own. A call made on the bridge's own thread is refused at once.

The other clients run there only through the `-linux` crates' integration tests, still against their fakes.

**Clients of Eileen's own.** Where this table first named `ashpd`, `ksni` or `atspi`, WP10 writes the D-Bus client itself on `zbus` 5.19.0, as it did for MPRIS and the desktop-entry parser. BUILD.md section 4.1 pins none of the three, and the portal client they would bring already exists: `eileen-dbus-linux`'s `Request`, which the OpenURI and Inhibit portals use. A client of Eileen's own keeps the deadlines, the sender checks and the error rules of the other clients, on the zbus build the workspace has, tokio only. On `main` are the GlobalShortcuts client (#93) and its holder (#107), the tray's item and menu served with `#[zbus::interface]` (#110) and the AT-SPI2 client (#87), and, written the same way, the RealtimeKit client (#90).

**Deadlines.** None of the methods the Linux adapters serve takes a `Deadline` on `main` yet (`Apps::main_window` does, and answers `Unavailable`), so each adapter waits at most `eileen-dbus-linux`'s `DEFAULT_DEADLINE`, the 5 s method timeout plus half a second, and past it answers `DeadlineExceeded` naming the call. Two seams change that, for a caller that needs an answer sooner and for the tests that hold a call past its deadline: `LinuxShellSettings::deadline`, `LinuxAudioSettings::deadline` and `LinuxMedia::new_within` take a deadline of their own, and `LinuxApps::reading_files_on` and `Opener::checking_files_on` run the file reads and checks on a runtime's blocking pool the caller gives, which caps the threads that hung reads keep. A read that another process can hold, such as a file on a FUSE or NFS home, runs on a named thread of its own within the deadline (`bounded` in `eileen-apps-linux`), and past it is left to that thread. BUILD.md section 3.4 has given the file-reading methods the caller's `Deadline` since #76, and the owner's #77, open, changes their signatures in `eileen-platform`. WP10's #116, ready and based on #77, moves `LinuxApps` and `LinuxRecent` to them, so that once both merge they read within the caller's deadline in place of `DEFAULT_DEADLINE`; `set_run_at_sign_in`, which then takes the deadline without enforcing it, is to write its entry on a helper thread within it. When the two merge is the owner's call.

`MachineProbe` reads these sources, all without elevation. The readers are in `crates/eileen-shell-linux`.

- **CPU.**
  - The name, the vendor and the features come from `/proc/cpuinfo`: `avx2`, `avx512f`, `avx_vnni` or `avx512_vnni`, and Arm's `asimd` and `asimddp`. An Arm kernel whose `cpuinfo` names no processor gives the chip's name instead, from `/sys/devices/soc0` or the device tree's `compatible` list.
  - Logical processors are the `online` list. Physical cores are the distinct `topology/core_cpus_list` sets, because `core_id` restarts in each Arm cluster.
  - Core classes come from Intel's hybrid PMU lists (`cpu_core`, `cpu_atom`), which give the same two classes Windows reports. Otherwise they come from distinct `cpu_capacity` values (Arm big.LITTLE), and otherwise there is one class.
- **GPUs and NPUs.**
  - Adapters come from `/sys/class/drm/card*/device/uevent`: the driver, the PCI ids and the slot, with names from `pci.ids`. Display-only and virtual adapters are left out.
  - NVIDIA GPUs are discrete, and NVIDIA's own driver also lists them under `/proc/driver/nvidia/gpus`, which finds them when `nvidia-drm` has made no DRM card. Intel's are integrated at slot `00:02.0`.
  - An amdgpu GPU is integrated only beside an AMD processor. When the processor's name mentions Radeon, it is the AMD GPU with the least VRAM, whatever the carve-out (a Strix Halo's can be 96 GB). Otherwise it is one whose VRAM is a carve-out of 2 GB or less with more GTT than VRAM, as on desktop Ryzen 7000 parts. VRAM and GTT are the dedicated and shared memory; an integrated GPU's carve-out counts as dedicated, as Windows reports it.
  - An Arm chip's own GPU (panthor, panfrost, msm and others) is integrated and has no PCI id.
  - NVIDIA's own driver gives the model and the driver version from `/proc/driver/nvidia`. The GPU's UUID in the same file is never kept.
  - NPUs come from `/sys/class/accel`.
  - Under WSL the GPU is `/dev/dxg`, with no DRM card, so the adapters are listed as degraded.
- **Disk.**
  - `statvfs` on the data folder gives the space, or on its nearest existing parent before setup creates it.
  - The block device's `queue/rotational` gives the media. The device is found by its number in `/sys/block`, partitions, LVM and LUKS included, or through `/proc/self/mountinfo` for btrfs, whose device numbers match no device.
  - WSL's and virtual machines' disks claim to rotate, or claim to be solid-state for a network volume. They are reported as `Unknown` and degraded, never as hard disks. A guest is known by WSL's kernel release, the CPU's `hypervisor` flag or Xen's `/sys/hypervisor`, and otherwise (an Arm guest) by its disks' names and models.
- **OS.** `/etc/os-release`, or `/usr/lib/os-release`, and the kernel release: `ubuntu 24.04, kernel 6.8.0-45-generic`. The build changes with each kernel update, as Windows' update revision does, so benchmarks that depend on it run again.
- **Power.**
  - The battery comes from `/sys/class/power_supply`. A battery whose scope is `Device`, such as a mouse's, is not the PC's.
  - Battery saver is the ACPI platform profile `low-power` or power-profiles-daemon's saved `power-saver` profile.
  - `UPower` gives the battery and the power source over D-Bus (`LinuxPower` in `crates/eileen-shell-linux`): `OnBattery`, and its devices of `Type` 2 with `PowerSupply` and `IsPresent`. A desktop on a discharging UPS reports `on_battery` without `has_battery`.
  - L1 reads the active profile over D-Bus (`LinuxPower` in `crates/eileen-shell-linux`): `ActiveProfile` under `org.freedesktop.UPower.PowerProfiles`, else `net.hadess.PowerProfiles`, which also sees a program's hold.
- **Monitors.** The DRM connectors whose status is `connected` and that are not `disabled`.
- **Load.** `MachineProbe::load`'s CPU busy share comes from the `cpu` line of `/proc/stat`: busy ticks over all ticks since the previous call, as `GetSystemTimes` differences give it on Windows. The power state comes with it.

## 5. Processes, IPC and security on Linux

The Windows design's safety rests on Job Objects, named-pipe caller checks and per-user folders. Linux has an equivalent for each.

- **Supervision.** On `main`, `eileen-supervisor` starts every child as the leader of a session of its own (`setsid`), so it has no controlling terminal and a prompt on `/dev/tty` fails at once instead of stopping it, and kills it with its whole process group (#106, for SU1, SU3 and SU6 of the review of #73).
  - Each child gets `SIGKILL` as its parent-death signal (`PR_SET_PDEATHSIG`), so a crash of Eileen kills every child. It is forked on the supervisor's own long-lived thread, `supervisor.fork`, because the parent-death signal follows the thread that forked the child, not the process. The kernel clears the signal on fork, so it never reaches grandchildren, and a set-user-ID program run as a child loses it at exec.
  - A pidfd per child says when the leader has exited. Its group is killed on drop, on `start_kill`, and when `wait` or `try_wait` sees the leader exit, always before tokio reaps it, so no reused PID is ever signalled. Nothing calls `waitpid` by PID or group. The pidfd needs Linux 5.4 or later (`pidfd_open` from 5.3, `waitid(P_PIDFD)` from 5.4), and `eileen_supervisor::spawn` on Linux needs a tokio runtime with I/O enabled: outside one it returns an error.
  - Descendants that outlive their leader in a crash, or leave its group, are not reached: they are for the cgroup scope below, which the supervisor does not have yet, and until then they run on.
  - stdout carries the protocol. On every OS `eileen_supervisor::spawn` forwards a child's stderr into `child.stderr` events from the start, so a child that fills stderr cannot hang its caller, whether the caller waits, polls `try_wait` or reads stdout to its end first; a `ChildSpec` with `raw_stderr` hands the caller the pipe instead, which it must then read (#118, finishing SU5, after #115 drained it in an awaited `wait` on Linux).
  - Containment uses cgroup v2, and is planned. Each Claude session runs in a transient user scope (`systemd-run --user --scope`) or a sub-cgroup of Eileen's delegated slice. Killing the scope with `cgroup.kill` takes the grandchildren too, which is the property BUILD.md's "killing a supervised child's Job Object kills its grandchild" test asks for.
  - `memory.worker_job_limit_mb` maps to the scope's `MemoryMax`, and the scope's `memory.events` OOM count becomes `WorkerEvent::MemoryLimit`, as `JOB_OBJECT_MSG_JOB_MEMORY_LIMIT` does on Windows.
  - The guard starts outside Eileen's scope, as it starts outside the Job Object on Windows. On Unix `spawn_detached` starts it as the leader of a new process group, and the core reaps it on a thread of its own, `supervisor.reap`, so a guard that exits leaves no zombie, and a liveness check by its PID no longer reports a dead guard as alive for the rest of the core's life (#117, for SU2). It is still a check by PID, so once the guard is reaped its PID can go to another process; a check that must be exact needs a pidfd opened while the guard runs.
  - `process-wrap` 10.0.1, already pinned, has `process-group` and `process-session` features for Unix. On Linux the supervisor uses neither: `setsid` and the parent-death signal are set in its own pre-exec setup. Its manifest turns `process-group` on, which only its code for Unix systems other than Linux uses, and BUILD.md section 3.1 lets a member add features to a dependency other than `windows`, `windows-sys` and `tokio`, so no root manifest amendment is needed.
- **Scheduling.** There is no EcoQoS on Linux to opt out of.
  - Audio threads ask RealtimeKit for real-time priority. That needs the process's hard `RLIMIT_RTTIME` lowered first (section 4), and the limit reaches past the audio thread. It is process-wide. Every child spawned after it is set inherits it, and the core starts the speech, desktop, apps and HUD processes, the guard and every Claude session (BUILD.md 2.1 rule 1). It cannot be raised again without `CAP_SYS_RESOURCE`. It counts the CPU time a thread under a real-time policy uses without a blocking system call, so an audio thread that waits on its device every period stays far below it. When a real-time thread runs past the soft limit, the process gets `SIGXCPU`, whose default action ends it, and `SIGKILL` at the hard limit; with the soft limit equal to the hard one, as `eileen-audio-linux` sets it when the soft one was unlimited, `SIGKILL` comes with no `SIGXCPU` first. In the core, either costs everything (BUILD.md 2.1). Which process sets the bound first is WP4's wiring.
  - A `ClaudeSession` child runs `CLAUDE_SESSION_NICER_BY` (10) nice steps below the thread that forks it, at most at 19, set between fork and exec so its builds inherit it; `Sidecar` and `Tool` children keep that thread's value (#115, SU4). The value is raised from the forking thread's rather than set, so a core already running nicer never asks for a lower value, which needs privilege. A nice value orders tasks only within one CPU cgroup, or, where the kernel's autogroup applies (on by default on Ubuntu, and only for tasks in the root CPU cgroup), within one session's autogroup. Each child's `setsid` starts a new autogroup, so there its builds still get an equal share against the core's; that share is the cgroup scope's CPU weight to set.
  - Builds under `cargo xtask` run 10 nice steps down: on Unix the build guard runs cargo through `nice -n 10` in a process group that a `/bin/sh` watchdog leads and kills with `SIGKILL` once the guard's pipe closes, however `cargo xtask` ends (#108, for BU5).
  - Idle I/O priority, for Claude sessions and builds alike, waits for an `ioprio_set` call (or `ionice -c 3`), which neither the supervisor nor the build guard makes yet.
- **Thread names.** Linux keeps 15 bytes of a thread name, and std cuts a longer one without a word before `pthread_setname_np`; the kernel's copy is what `/proc/<pid>/task/<tid>/comm`, `top -H`, gdb and core dumps show. On Linux `eileen_rt::runtime::build` names its threads `<name>-rt` and takes a runtime name of at most 12 bytes; a longer one fails a soft assertion and is cut to its first 12 bytes (#105). WP10's own names and the ones its amendments added fit: `eileen-dbus` and `eileen-dbus-blk` in the bridge, `supervisor.fork` and `supervisor.reap`, and `eileen-trace`'s `eileen-log`, `eileen-console` and `eileen-flush` (#86, #92). `eileen_stdx::thread::spawn_named` checks no length yet.
- **Pipes become Unix sockets: the `ipc` module on Linux.** The speech pipe, the dispatcher pipes and the session sockets live under `$XDG_RUNTIME_DIR/eileen/`, mode 0700. They are the Linux forms of decision D86's `ipc` module in `eileen-supervisor`, which WP2 builds for Windows (`wp2/supervisor-pipes` and `wp2/supervisor-callers`, BUILD.md 6.4 items 3 and 4; neither is on `main` yet). The module's types exist on every OS, and until WP10 builds the forms below, every `ipc` call on Linux answers `Unsupported`, so no Linux build accepts a caller it could not check (BUILD.md 2.12). WP10's record lists the pull requests that build them ([docs/wp/WP10-linux.md](wp/WP10-linux.md), Planned) and what the module's interface can keep neutral for them (Findings for other packages). For each Windows behaviour of BUILD.md 3.1's interface, the Linux mechanism, what it guarantees and what it does not:
  - **The server's socket** (`PipeServer::bind` and `accept`).
    - Mechanism: a stream Unix socket bound to a path in `$XDG_RUNTIME_DIR/eileen/`, over tokio's `UnixListener` (the `net` feature, already in the union). The folder is made with mode 0700 and opened with `O_DIRECTORY` and `O_NOFOLLOW`; its owner must be the process's effective user and its mode must grant nothing to group or others (`fstat`), or no socket is bound and no token written. Later steps go through that descriptor, so a folder renamed or replaced after the check is not the one used [inferred: a socket is bound through `/proc/self/fd/<n>/<name>`; the pull request settles how].
    - Guarantees: a path socket honours the permissions of its folder, and connecting to one needs write permission on its file ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)), so only the user's processes, and root's, reach it. A Unix socket is never reachable from another machine, which is what `PIPE_REJECT_REMOTE_CLIENTS` gives on Windows, and the server takes a client only when `SO_PEERCRED`'s user id is its own.
    - Failing closed: `bind` answers `EADDRINUSE` when the path exists ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)), whether a socket listens there or not, and a socket's file outlives a crash, where a pipe goes with its last handle. The per-session names (`eileen-speech-<session>` and `eileen-dispatch-<session>`, with the runtime's new `sess_` id each run) never meet an earlier run's file; a fixed name (`eileen-dispatch-owner`, the guard's socket) can. So on `EADDRINUSE` the server connects to the path once, without blocking (tokio's `UnixStream::connect`) and within the caller's deadline, since a listener whose backlog is full and never accepts would hold a blocking `connect`: only `ECONNREFUSED`, which says nothing listens, leads the server to remove that stale file and bind once more. Any other answer (a listener that takes the connection, `EAGAIN` from a full backlog, `EACCES`, the deadline passing), or a second `EADDRINUSE`, is `NameTaken`, as on Windows. A same-user process that binds between the removal and the second bind makes it fail closed.
    - Not given: one listening socket takes every connection, so Windows' next instance has no Linux form, and what `accept` cannot do (out of descriptors, `EMFILE`) is the incident Windows raises for an instance it cannot make. A same-user process can still remove the socket's file and bind its own at the name, the Linux form of adding a pipe instance (BUILD.md 2.12), so, as on Windows, every client checks the server first (below). The core also watches its folder with inotify, so a socket file removed or replaced is an incident, not a silent loss of the name [proposed].
    - Abstract sockets are ruled out. Their names have no permissions ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)), so any process of any user in the same network namespace can take a name first or connect to it, sandboxed apps that share the host's network included [inferred].
    - Names: `sun_path` holds 108 bytes ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)), so the names stay short, and a folder deep enough to push one past it, such as a test's `EILEEN_DATA_DIR` under a long temporary path, fails at `bind` rather than being cut.
  - **Both ends' process ids** (`PipeConn::client_pid`, `server_pid` and `since`).
    - Mechanism: `SO_PEERCRED`, which tokio's `UnixStream::peer_cred` reads with no unsafe code. The server reads the client's credentials as they were at its `connect`, and the client reads the server's as they were at its `listen` ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)). `since()` reads the boot clock (`CLOCK_BOOTTIME`, rustix's `time` feature) at the accept or the connect, the clock in which `/proc/<pid>/stat` gives a process's start [inferred: the kernel reports the task's boot-based start time].
    - `SO_PEERPIDFD` (Linux 6.5, [kernelnewbies](https://kernelnewbies.org/Linux_6.5)) also gives a pidfd of the peer, which refers to that process and no other, whatever its PID becomes. rustix 1.1.5 does not wrap it (its `net::sockopt` has `socket_peercred` and no pidfd option), so it is one `getsockopt` in the supervisor's `ffi` module with `libc`, whose 0.2.190, already in the lock, defines `SO_PEERPIDFD`, but which BUILD.md 4.1 does not pin: that takes its own amendment, unless a rustix release that wraps it comes first. Until then `Peer` opens `SO_PEERCRED`'s PID by its number and checks the start time (below).
    - Not given: the credentials name the process that connected, not one that holds the descriptor later (inherited, sent with `SCM_RIGHTS`, or taken with `pidfd_getfd`, which needs ptrace attach rights ([pidfd_getfd(2)](https://man7.org/linux/man-pages/man2/pidfd_getfd.2.html)) that Ubuntu's Yama scope 1 grants only over descendants, [ptrace(2)](https://man7.org/linux/man-pages/man2/ptrace.2.html)). A PID from another PID namespace reads as 0, so the core, its sidecars and the shims must share one, which L3's Flatpak package must keep [inferred]. Whether Ubuntu 24.04's kernel answers `SO_PEERPIDFD` for a peer that has already exited with an error or with a pidfd of the dead process is [inferred]; either way the peer is refused.
  - **`Peer`, one open of the other end.**
    - Mechanism: the peer's `/proc/<pid>` folder, opened once (`O_DIRECTORY`), and every fact read through that descriptor (`stat`, `exe`, `cgroup`). With a pidfd from the socket, the folder is the peer's when `pidfd_send_signal(pidfd, 0)` still succeeds after it is open ([pidfd_send_signal(2)](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html), Linux 5.1), since a PID is not reused while its process, even a zombie, exists ([pidfd_open(2)](https://man7.org/linux/man-pages/man2/pidfd_open.2.html)). Without one (`tcp_client_pid`'s answer, or no `SO_PEERPIDFD` yet) the folder is opened by its number, and the peer is refused when field 22 of its `stat`, its start in clock ticks since boot ([proc_pid_stat(5)](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)), is later than `since`.
    - Guarantees: the `/proc/<pid>` descriptor is itself a PID file descriptor, a stable reference to the process it was opened on, which `pidfd_send_signal` refuses with `ESRCH` once that process has ended and been reaped ([pidfd_send_signal(2)](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html)), so the checks can confirm the peer still runs after reading its facts. That the reads through it fail too once the process is gone, even if its PID is reused, is [inferred: the pull request's test reads through one after its process exits]. Reading `exe` takes a `PTRACE_MODE_READ_FSCREDS` check ([proc_pid_exe(5)](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html)), which a process of the same user passes unless it is not dumpable, and which Yama does not restrict ([ptrace(2)](https://man7.org/linux/man-pages/man2/ptrace.2.html)).
    - Not given: the start time counts ticks, 100 a second here (`getconf CLK_TCK`), where `GetProcessTimes` counts 100 ns, so without a pidfd a process that took the PID within the same 10 ms as the accept passes that check. Both Ubuntu releases have `SO_PEERPIDFD` (the table below), so once the supervisor reads it, the window there is `tcp_client_pid`'s alone. A process that is not dumpable (a set-user-ID program, or one that called `PR_SET_DUMPABLE`) gives no facts and is refused, as a process that cannot be opened is on Windows. The second field of `stat` is the process's name in parentheses, which can itself hold `)` and spaces, so the parser reads the fields after the last `)`; it parses untrusted input and gets a fuzz target (BUILD.md 4.7).
  - **`PeerFacts`: the image and the install folder.**
    - Mechanism: `image` is `readlinkat` of the peer's `exe`, given only when the file the link reaches (`statx` through it) is the file at that path now, the same device and inode. It is `None` for a link that cannot be read (the main thread has exited, [proc_pid_exe(5)](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html)), a path that is not UTF-8, and a file removed or replaced since the process started, whose link reads `<path> (deleted)`. The install folder is the folder of the checker's own `/proc/self/exe`, as on Windows, so L3's packages keep `eileen`, `eileen-shim` and `eileen-speech` in one folder (a `/usr/bin/eileen` link to it is fine, since `exe` holds the resolved path).
    - Not given: a process that runs through an update of Eileen sees its file replaced and is refused until it restarts. The check proves which file the process runs, no more: from a folder the user can write (a build in `target/`, a per-user install) any same-user process can put its own program in its place, as with a per-user install on Windows; a `.deb` install under `/usr`, owned by root, is what gives the image check its weight.
  - **The `Jobs` registry and the caller's job.**
    - Until the cgroup scope (under Supervision above) exists, a job on Linux is the session each child's `setsid` gives it (#106). Each registry entry keeps its child's session id, which is the child's own PID since the child leads the session, and the child's pidfd; `PeerFacts.jobs` holds the keys whose session the peer is in (field 6 of `/proc/<pid>/stat`), and `in_any_job` says whether it is in any. No call joins an existing session: `setsid` makes a new one and `setpgid` moves a process only within its own ([setsid(2)](https://man7.org/linux/man-pages/man2/setsid.2.html), [setpgid(2)](https://man7.org/linux/man-pages/man2/setpgid.2.html)), so a process in a job's session descends from that job's child while the session's number is still that session's. A number stays its session's only while some task holds it [inferred: the kernel frees a PID number only when no task holds it as a PID, a process group or a session]: once the leader is reaped (#106 kills its group and tokio reaps it) and the last member is gone, the number can go to a new process, whose `setsid` makes a session with the same id, while the registry entry still lives (BUILD.md 3.1 lets an entry outlive a restart). So a peer counts as in an entry's session only when `pidfd_send_signal(<the entry's pidfd>, 0)` succeeds after the peer's `stat` is read, which it does while the leader runs or is a zombie, and so still holds the number ([pidfd_send_signal(2)](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html)). An entry whose leader is reaped matches no session. Only that check keeps membership from being forged by a reused number.
    - Not given: any member can leave, with `setsid` after a fork (what `setsid(1)` and daemons do), which a Job Object without breakaway forbids on Windows. A member that outlives its leader in another process group (one that called `setpgid`, which #106's kill of the group does not reach) is in no job once the leader is reaped, as one that left is; the cgroup scope covers both. A process that leaves loses every role that needs the job, which fails closed, but it then passes the "outside every Eileen job" check of the session role and the loopback endpoints (BUILD.md 2.12), and so does anything a worker starts through the user's service manager (`systemd-run --user`) or D-Bus activation: BUILD.md section 7's open risk for the shell, WMI and the Task Scheduler, cheaper on Linux, until v0.2's sandbox. Whether the claude CLI keeps the shim and the hooks' connections in its own session must be measured before L1 relies on it [inferred]: a CLI that starts them in sessions of their own would fail every role closed. `job_memory_limit_mb` has no Linux form until the scope, and `memory_limit_hit` never resolves there; `RLIMIT_AS` is no substitute, since it bounds each process's address space, which V8 reserves far beyond what it uses [inferred]. `breakaway_ok` changes nothing on Linux, where nothing stops a process from leaving.
    - With the scope: each entry also keeps its scope's cgroup, killed with `cgroup.kill` (Linux 5.14, [kernelnewbies](https://kernelnewbies.org/Linux_5.14)) on drop, and `memory.max` with `memory.events`' `max` and `oom_kill` counts ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)) give the memory limit and `memory_limit_hit`. `in_any_job` then also counts a peer whose cgroup (the `0::` line of `/proc/<pid>/cgroup`, [proc_pid_cgroup(5)](https://man7.org/linux/man-pages/man5/proc_pid_cgroup.5.html)) lies under any entry's scope, but `jobs` stays by session: a scope that the user's service manager made belongs to the user, so a same-user process can write itself into its `cgroup.procs`, for which it needs write access to the `cgroup.procs` of the common ancestor ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)) [inferred: L1 checks the owner of a user scope's files on Ubuntu 26.04], and so forge the membership a session cannot.
  - **`tcp_client_pid`, for the hooks' loopback port.**
    - Mechanism: one sock_diag request ([sock_diag(7)](https://man7.org/linux/man-pages/man7/sock_diag.7.html), `NETLINK_SOCK_DIAG` since Linux 3.3) for the one TCP socket with the connection's addresses and ports, a query about an individual socket rather than a dump, which answers the socket's owner (`idiag_uid`) and inode number (`idiag_inode`); then a walk of `/proc/<pid>/fd` over the user's processes for the link `socket:[<inode>]`, as `ss -p` does ([ss(8)](https://man7.org/linux/man-pages/man8/ss.8.html)). rustix's `net` feature has the netlink socket, and the request and its answer are bytes built and parsed in safe code.
    - Not given: no call maps a socket to its process, so the walk reads every descriptor of every process of the user's, which costs [inferred: tens of milliseconds on a desktop with a browser open; L1 measures it] per connection, paid once at the accept, since a connection the hooks reuse keeps its owner [inferred]. A socket can be held by more than one process after a `fork`, where Windows' table names one owner, so `tcp_client_pid` names no process when the walk finds more than one, and the endpoint refuses. The PID it finds can be reused before `Peer` opens it, which only the start time (above) catches. Once the scope exists, the request's `INET_DIAG_CGROUP_ID` attribute (in Ubuntu 24.04's kernel headers, 6.8) names the socket's cgroup without a walk, but since a scope can be joined it narrows the walk to the scope's processes rather than replacing it. If the hooks reached the core through `eileen-shim`'s socket instead of HTTP, `SO_PEERCRED` would replace the walk: WP2's and WP3's choice, not WP10's.
  - **`write_user_only` and the token files.**
    - Mechanism: a temporary file in the same folder, made with `O_CREAT`, `O_EXCL` and `O_NOFOLLOW` and mode 0600, written, synced and renamed over the old name, which replaces it atomically ([open(2)](https://man7.org/linux/man-pages/man2/open.2.html), [rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)), so a token never sits in a file others can read, and a reader sees the old file or the new one, never a part. `O_EXCL` fails on any existing name, a planted symbolic link included. The umask only takes bits away from 0600 ([open(2)](https://man7.org/linux/man-pages/man2/open.2.html)), and a default ACL on the folder, which takes the umask's place, keeps no permission the mode does not hold ([acl(5)](https://man7.org/linux/man-pages/man5/acl.5.html)). `grants_only_user` reads back the owner, a mode with nothing for group or others and no access ACL (`fgetxattr` of `system.posix_acl_access`, rustix's `fs` feature), for the folder and for the file. Each token file gets the sticky bit, which the XDG specification names for runtime files that must not be cleaned up ([XDG Base Directory](https://specifications.freedesktop.org/basedir/latest/)); an owner may set it (`chmod 1600` works here).
    - Not given: a user-only mode keeps out other users, not the user's own processes, as the DACL does on Windows; what keeps a worker from `bus.json` is the path guard and the caller checks (BUILD.md 2.12).
  - **Where `run/` lives: `$XDG_RUNTIME_DIR/eileen/run/`**, proposed for the owner as a decision in WP10's record. BUILD.md 2.15's `run\` holds per-boot files only: the token files, `models.json`, the brain's and each session's settings, MCP configuration, plugin snapshot and `cwd`, and the guard's socket. The runtime folder is made for them ([XDG Base Directory](https://specifications.freedesktop.org/basedir/latest/)): the user's own with mode 0700, on a local file system shared with no other system, created at the user's first login, removed at the last logout and gone after a reboot. So a token never reaches a disk or a backup, a crash leaves no token behind past a reboot, and two machines that share an NFS home never write the same `bus.json`. `~/.local/state/eileen/run/` would do all three wrong: it persists, it can live on another host, and it is backed up with the home. The cost: the folder is in memory, under a size limit logind sets (10% of RAM by default [inferred]), so the session folders must stay small, and a session's `cwd` holds what it writes there. With `EILEEN_DATA_DIR` set, `run/` follows it, as everything else does, and the same checks apply. With no `XDG_RUNTIME_DIR` (a session logind did not start), the `ipc` calls answer an error that names it rather than fall back to a shared folder such as `/tmp`, where another user can take the name first. Under WSLg the variable is `/mnt/wslg/runtime-dir`, of mode 0777 without the sticky bit on this machine (measured 2026-11-10), against the specification's 0700, which is why Eileen checks its own folder's owner and mode and never relies on the parent's. The path classes gain the folder (below).
  - **The tokens** are 32 bytes from `getrandom` 0.4.3 (D86), as on Windows. On the glibc Linux targets, x86_64 and aarch64 among them, the crate's `linux_android_with_fallback` backend calls the C library's `getrandom` with no flags ([getrandom(2)](https://man7.org/linux/man-pages/man2/getrandom.2.html), Linux 3.17, glibc 2.25), which blocks only until the kernel's pool is first ready and then answers up to 256 bytes in full, with no interruption by a signal; it falls back to `/dev/urandom` only when the call answers `ENOSYS` or `EPERM` (read in 0.4.3's source). Nothing Linux-specific is to write.
  - **The server check every client makes first.** The speech process and `eileen-shim` read `server_pid()`, the listener's credentials, open it as a `Peer` from the socket's pidfd, and send their first line only when it is the core's PID they were given, with their own user id and an image of `eileen` from their own folder, as on Windows. The kernel fills `SO_PEERCRED`, so a process that took the name cannot pass for the core.

- **Path classes.** The classes of BUILD.md 2.12 need a Linux list.
  - The classification reads the OS only through the `PathProbe` trait (decision D86), which `eileen-shell-linux` is to implement on Linux (BUILD.md 3.4) once WP2's `wp2/path-probe-trait` adds it; until then a path that needs a probe is `Unknown` on Linux.
  - **`PathProbe` on Linux.** Each method that reads the disk runs on a named thread within the caller's `Deadline` and is left to that thread past it, as the `bounded` helper of `eileen-apps-linux` does (WP10's record, Still open, plans its move to where both crates can use it), since a path on an NFS or FUSE mount can hang. For each of the trait's answers:
    - Paths: BUILD.md 3.4 says the trait's paths are strings as Windows writes them; on Linux they are strings as Linux writes them (WP10's record, Findings for other packages, asks WP2 to say so). A Linux path is bytes, and one that is not UTF-8 is `Unknown`. The probe takes absolute paths only (the caller joins a relative path to the working folder, as on Windows), and the drive, UNC and `\\?\` forms do not occur.
    - `full_path` removes `.` and repeated slashes and never applies `..`, because POSIX resolves `..` in the folder a link leads to: `a/link/..` is the parent of the link's target, not `a`. `..` is `final_path`'s. It touches no disk.
    - Two readings of `..`: a program that hands the path to `open(2)` unchanged gets the kernel's reading, which `final_path` follows, but the claude CLI's file tools are Node code, whose `path.resolve` and `path.normalize` remove `..` by string, as `GetFullPathNameW` does on Windows [inferred: L1 checks how the CLI's Read, Write and Edit tools resolve a path]. The two differ only where a `..`, read by string, removes a component that is a symbolic link: with `~/job/l` a link to `/home/u/job/a/b/c`, the kernel reads `/home/u/job/l/../../.ssh/id_ed25519` as `/home/u/job/a/.ssh/id_ed25519`, and Node as `/home/u/.ssh/id_ed25519`. So `final_path` answers `Refused` for such a path, which the classifier takes as `Unknown`, whichever reading the tool uses; a `..` that removes a component that is not a link, or a missing one, reads the same both ways. Windows has no such split, because the OS and the CLI both read `..` by string there.
    - `final_path` walks from `/` one component at a time with `openat2`, `O_PATH` and `O_NOFOLLOW`, under `RESOLVE_NO_MAGICLINKS` ([openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html), Linux 5.6). It reads each symbolic link's target raw (`readlinkat`) and checks it before it follows it, resolves `..` in the folder it has reached, stops at the kernel's limit of 40 links ([path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)), and stops at the first component that does not exist. After it, the rest is read as a tool that creates the missing folders reads it: `.` is dropped, a `..` removes the missing component before it, and a `..` with no missing component left goes to the parent of the folder the walk has reached, where the walk resumes, through links, with the components after it. No missing component can be a link, so this is exact, and the missing parts never hold `.` or `..`, as on Windows, where `GetFullPathNameW` removed them first (WP10's record, Findings for other packages, point 7, asks WP2's fake to keep that). So `/home/u/job/newdir/../../.ssh/authorized_keys`, with `newdir` missing, ends in `/home/u/.ssh`, not in the job folder. The existing part's path is the kernel's own name for the last descriptor (`readlink` of `/proc/self/fd/<n>`), as on Windows it is `GetFinalPathNameByHandleW`'s. An `O_PATH` open does not open the file itself ([open(2)](https://man7.org/linux/man-pages/man2/open.2.html)): no FIFO waits for a writer, no socket connects and no device's open runs.
    - Which paths a probe opens: only components of absolute paths outside `/proc`, `/sys` and `/dev`, whose names reach processes, kernel objects and devices (`/proc/<pid>/fd/<n>`, `root` and `cwd` are magic links, which `RESOLVE_NO_MAGICLINKS` refuses anyway), and outside every FUSE mount a user made, which shows whatever its program chooses under new names or reaches other hosts (below; the document portal's `doc` and GVfs's `gvfs` in the runtime folder among them). A path in a process's folder of `/proc` (`/proc/<pid>/`, `/proc/self/` or `/proc/thread-self/`), written so or reached as a link's target, is answered unopened as `FinalPath { existing: "/", missing: <its components> }`, so the classifier sees the `/proc` path and applies `Credential` (below); it is the one answer whose missing parts may exist (WP10's record, Findings for other packages, point 7, asks WP2 to class it by the path alone), and one with `..` after `/proc` is `Refused`, since `/proc/self/cwd/..` is the parent of a working folder, not of `/proc/self`. Any other path in `/proc` (`/proc/mounts`, `/proc/net`, `/proc/cpuinfo`), any path in `/sys` or `/dev`, a path on a FUSE mount a user made (the walk stops at its mount point, below), a link that points into one, and an automount point (`statx` with `AT_NO_AUTOMOUNT`, [statx(2)](https://man7.org/linux/man-pages/man2/statx.2.html)) answer `Refused` unopened, which the classifier takes as `Unknown`, so classifying a path never mounts anything [inferred: L1 checks an autofs and a systemd automount]. Contents are read only from regular files, desktop entries and `mimeapps.list`, opened with `O_NONBLOCK` and `O_NOCTTY` after the walk and read to at most 1 MiB, as the app index does (#67).
    - `link_names`: Linux gives a file's link count (`statx`), but no call lists its other names, which only a walk of the whole file system finds, so the probe fails closed by itself: for a file that is not a folder and whose count (`statx`'s `stx_nlink`) is above one it answers `Refused`, which the classifier takes as `Unknown` (tier 2, asked), and for any other, a folder included, it answers every name the mounts give it (under `share` below), which is the one name it was given where no second mount holds it. Where Windows classifies a file under each of its names, a hard link in a job folder to `~/.ssh/id_ed25519` is so asked about on Linux, not read at tier 0, with no rule in WP2's neutral classifier; WP10's record, Findings for other packages, point 8, suggests a trait that carries the count, which would let the classifier say it on any OS, but the probe does not depend on it. The cost is a question for files that cargo and git link (`target/`, the objects of a local clone) [inferred: L1 counts how often]. `fs.protected_hardlinks` does not help, since a credential is the user's own file.
    - `short_path` answers `None`: Linux file systems keep no 8.3 names. On vfat and on WSL's Windows drives (`/mnt/c` is a `9p` mount of `C:\` on this machine) the alias may still open the file [inferred], so the `GIT~<n>` rule applies by file system there, as the `.git` spelling rules do (below).
    - `share`: no Linux path has a host and a share, so the classifier never asks it. What it guards against on Windows, a probe that reaches another host or a second name for a local file, comes from the mount of the final path in `/proc/self/mountinfo` ([proc_pid_mountinfo(5)](https://man7.org/linux/man-pages/man5/proc_pid_mountinfo.5.html)), found by the mount id `statx` gives for the last descriptor (`STATX_MNT_ID`, Linux 5.8, [statx(2)](https://man7.org/linux/man-pages/man2/statx.2.html)) and read with the parser `eileen-shell-linux` has, and fuzzes, for the disk facts. On a network file system (`nfs`, `nfs4`, `cifs`, `smb3`, `ceph`, `fuse.sshfs` and the like) every access reaches the server with the mount's credentials, as every program of the user's does, so the probe reads it only within the deadline. A network mount whose source names this machine (`localhost`, a loopback address, its own host name) shows local files under another path: `final_path` answers it `Refused`, so it is `Unknown`, as another share of this machine is on Windows.
      - A FUSE mount gets a new anonymous device, so the device rule below cannot see a second name on it, and a user needs no privilege to make one on Ubuntu (`/usr/bin/fusermount3` is set-user-ID root here): `bindfs ~/.ssh ~/job/m`, `fuse-overlayfs` with `~/.ssh` as its lower folder, or a small pass-through program shows `~/.ssh/id_ed25519` as `~/job/m/id_ed25519`, as a hard link would. So the walk reads the mount of each component it reaches (`statx`'s `STATX_MNT_ID`) and stops with `Refused` at the first on a mount of type `fuse`, `fuse.*` or `fuseblk` whose `user_id=` option (in field 11, the super options), the mount owner's user id ([FUSE](https://docs.kernel.org/filesystems/fuse/fuse.html)), is not 0, or that has none: a mount a user made [inferred: `fusermount3` sets `user_id` to its caller's user id and refuses one the caller gives], the user's own `sshfs` and the runtime folder's `doc` and `gvfs` among them, which are `Unknown`, the tier `Elsewhere` would give a remote one anyway. A FUSE mount the system made (`user_id=0`, such as an NTFS drive that udisks mounts with `ntfs-3g`) classifies as written. The pull request's tests have a FUSE mount line of each kind in a recorded `mountinfo`.
      - Second names on one device are found by device, not by a mount's root: a root (field 4) other than `/` is no sign of one, since a btrfs subvolume's mount has a root such as `/@` or `/@home` (Ubuntu's and Fedora's layouts), and a second mount of a whole file system has the root `/`. The file's path within its file system is its mount's root joined with the rest of the final path. Every mount of the same device (field 3, `major:minor`) whose root is that path or a folder above it holds the file, under its mount point joined with the rest of that path below the mount's root. No one of those names is the right one to keep: with `/home` an fstab bind of `/srv/home` on the root device, `/` (root `/`) and `/home` (root `/srv/home`) both hold `/home/u/.ssh/id_ed25519`, and keeping the mount whose mount point is shortest would keep `/srv/home/u/.ssh/id_ed25519`, outside `~/.ssh`, and make every job folder under `/home` `Unknown`. So `final_path` answers the name its walk reached, and `link_names` answers every name, of a folder as of a file, for the classifier to classify each, as Windows' classifier does a file's hard links (BUILD.md section 2.12); `Refused` is left for a file whose names cannot be computed (its mount missing from `mountinfo`, or a mount point that is not UTF-8). A name is answered even where another mount hides it, since an extra name can only add a class. Subvolumes whose roots do not nest (`/@` at `/` and `/@home` at `/home`) give one name each.

    - `shortcut_target`: a symbolic link's target, read raw and never followed, and a desktop entry's `URL` (`Type=Link`) or `Exec` (`Type=Application`) as written, field codes unexpanded ([Desktop Entry Specification](https://specifications.freedesktop.org/desktop-entry/latest/)). ## 9. Risks

- **Wayland's consent model.** Input and capture need the user's yes in a portal dialog, at least once, and some Windows behaviours have no Linux form. The Linux machine panel and the docs say plainly what works on which desktop.
- **The HUD on GNOME.** An honest overlay may need a GNOME Shell extension in JavaScript, a second language in the repository, which is an owner decision.
- **Contracts shaped by Windows.** `hwnd: i64` and physical virtual-screen pixels have no Wayland meaning.
  - On Linux, the window handle is an AT-SPI object reference mapped to an `i64` inside the `-linux` crate.
  - Element boxes are window-relative.
  - A contract that cannot express Linux gets an amendment, not a workaround.
- **Autostart paths.** A program path with `%` or a backslash cannot go into an autostart entry, because systemd's autostart generator, which starts the entries of KDE Plasma's sessions, reads it differently from the specification. `set_run_at_sign_in` refuses such a path when it writes the entry.
- **Keeping the session awake.**
  - Before systemd 257, logind's block lock does not stop the user's own `Suspend()`, so on Ubuntu 24.04 the desktop's hold must cover suspend too.
  - xdg-desktop-portal's Inhibit checks no lockdown setting and never answers `NotAllowed`. A permission store that masks every flag leaves the request unanswered, so it shows only once the deadline has passed.
- **Native build dependencies.** PipeWire's binding needs `libpipewire-0.3-dev`, `pkg-config` and `clang` at build time, in CI and on developer machines. Everything in L0 and L1 is pure Rust.
- **The runner image change.** `ubuntu-latest` changes from 24.04 to 26.04 during the current rollout, and tool versions with it. Pinning the image keeps a pull request's result from changing under it.

## 10. What the Linux lane found already

Running the PR lanes on Ubuntu 24.04 over the then unmerged `wp0/base-crates` work (`backup/wp0-base-crates` at ca336be) gave 305 of 305 tests passing and two failures that the Windows jobs cannot show. Reading the build guard's Linux memory code then showed a third problem, which no test exercised. All three are fixed on `main`: the base crates merged as #73 (a67d096) with a fix for each, as the write-up below proposed. The three findings are kept here as the lane found them.

- **A Linux-only clippy error.** In `eileen-supervisor`, `qos.rs` line 106, the test `an_audio_boost_reverts_on_drop` calls `drop(boost)`. Off Windows, `AudioBoost` holds no MMCSS handle and implements no `Drop`, so `clippy::drop_non_drop` fails the build under `-D warnings`. A `cfg_attr(not(windows), expect(clippy::drop_non_drop, reason = "..."))` on that statement, or ending the scope instead of calling `drop`, fixes it. #73 ends the boost with its scope.
- **A yanked pin.** `tokio` 1.54.0, BUILD.md 4.1's pin, is yanked on crates.io, so `cargo deny --locked check` fails. 1.54.1 appeared on 2026-10-21. The newest release outside the 14-day window was 1.53.2, of 2026-10-03. Pull request #27 moved BUILD.md 4.1's pin and the root manifest to 1.53.2, and #59 then to 1.53.3 for RUSTSEC-2026-0386. #73 locks section 4.1's pin, so `main` locks 1.53.3.
- **Commit headroom that Linux does not enforce.** On Linux the guard reads commit headroom as `CommitLimit` minus `Committed_AS`. The kernel enforces that limit only under strict overcommit (`vm.overcommit_memory = 2`). In the default mode, 0, `Committed_AS` can pass `CommitLimit` on a busy desktop, because browsers and runtimes reserve far more than they touch [inferred: the measurement below shows the mechanism, not how often a real desktop reaches it]. The headroom then reads 0 while gigabytes are free, and slot 0's rule refuses every build.
  - Measured on 2026-10-21, WSL2 with 16 GB and default overcommit: a 12 GB mapping that is never touched left `MemAvailable` at 13,957 MB but took the headroom from 9,691 MB to 0. Slot 0's rule, at the default 2,048 MB floor plus a two-job build's 2,048 MB estimate, went from admitting to refusing.
  - The fix that matches the kernel's policy is the one `LinuxSystemMemory` uses: under strict overcommit, keep `CommitLimit` minus `Committed_AS`; otherwise use `MemAvailable` plus `SwapFree`, the memory that can still be backed before the OOM killer acts. The guard and the runtime write the same machine-wide sample files, so both should use the same rule. #73's guard reads commit headroom by `vm.overcommit_memory`, as `LinuxSystemMemory` does.

`main` itself passes the whole lane on Ubuntu 24.04: at 5a4b11b, CI's `logic-linux` job ran 948 of 948 tests (run 40238334151), and at a84c198 1057 of 1057, the 4 `linux_session` tests skipped (run 40414356056).

## 11. Developer setup on Ubuntu, without sudo

This is the setup the local Linux lane runs on: Ubuntu 24.04 under WSL2 on Windows 11, with every tool under the home folder and no `sudo`. It runs every check of CI's `hygiene` and `logic-linux` jobs. A native Ubuntu install or a virtual machine works the same way. Since #98, `cargo xtask setup` runs step 2's `rustup toolchain install`, installs step 3's tools once cargo-binstall is there, and sets the git hooks, and `cargo xtask ci` runs step 4's lanes through the build guard ([DEV-SETUP.md](DEV-SETUP.md)). The steps below do the same by hand.

1. **Ubuntu.** On Windows 11, `wsl --install -d Ubuntu-24.04` in PowerShell (an administrator one the first time) gives a Linux shell in minutes. WSL2 runs the neutral crates and every PR lane, but it is not a Linux desktop (section 6). The desktop work of L1 and L2 needs an Ubuntu 26.04 desktop: a virtual machine (Hyper-V, VirtualBox, QEMU) or a spare PC.
2. **Rust, as the repository pins it.** rustup installs into `~/.rustup` and `~/.cargo`. Then, inside the clone, `rustup toolchain install` reads `rust-toolchain.toml` (1.99.0 with rustfmt and clippy), as CI does:

   ```sh
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --no-modify-path --default-toolchain none
   . "$HOME/.cargo/env"            # once per shell, or add it to ~/.bashrc
   git clone https://github.com/Sixteen1-6/eileen.git && cd eileen
   rustup toolchain install
   rustup default 1.99.0           # so cargo also runs outside the clone
   ```

3. **The CI tools, prebuilt, at CI's versions.** BUILD.md 4b's rule is never to `cargo install` from source:

   ```sh
   curl -sSfL https://github.com/cargo-bins/cargo-binstall/releases/download/v1.26.0/cargo-binstall-x86_64-unknown-linux-musl.tgz \
     | tar -xz -C "$HOME/.cargo/bin"
   cargo binstall --no-confirm cargo-nextest@0.9.148 cargo-deny@0.20.2 cargo-machete@0.9.2
   ```

4. **The lanes.** These are CI's `hygiene` and `logic-linux` steps, in order:

   ```sh
   cargo fmt --all --check
   cargo deny --locked check
   cargo machete
   cargo clippy --workspace --all-targets --locked -- -D warnings
   cargo nextest run --workspace --locked --profile ci
   cargo test --workspace --doc --locked
   RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --locked
   ```

5. **Optional: Windows clippy from Linux.** `rustup target add x86_64-pc-windows-msvc` installs the Windows standard library. After that, `cargo clippy --workspace --all-targets --locked --target x86_64-pc-windows-msvc -- -D warnings` finds most Windows-only compile errors before a push, as long as no dependency compiles C. Test binaries cannot link without MSVC's `link.exe`, so `windows-test` still runs only in CI.

Later phases need system packages, which do need `sudo`: `pkg-config`, `clang` and `libpipewire-0.3-dev` for PipeWire's bindings (L2), `libasound2-dev` beside `pkg-config` once `cpal` joins the Linux target tables, which BUILD.md section 4.1 does not allow yet (`cpal` 0.18.2 takes `alsa` 0.11 on Linux whatever its features, and `alsa` takes `alsa-sys` 0.4, which links libasound through pkg-config), and `weston` for the headless desktop lane (L1).
