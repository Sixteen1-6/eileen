# Learning the person through the models' own memory

Research pass, 2026-10-22, condensed on 2026-10-25 for decision [D77](../DECISIONS.md#d77-learn-the-person-through-the-models-own-memory-use-each-tools-native-strengths-and-adopt-the-ten-learning-ideas). The owner's direction of 2026-10-22 ([OWNER-DIRECTION.md](../OWNER-DIRECTION.md#2026-10-22)) asks Eileen to learn the person through the memory and personalisation the model vendors already ship in their official tools, and to use every native advantage of the tools it routes to instead of rebuilding them. This note answers three questions. What does each route's official tool already learn about the user, where is it kept, and what can an orchestrator control? Which of those can Eileen build on without breaking its hard rules? And what must Eileen still build itself?

It condenses four working notes (Anthropic, OpenAI, the other routes and shared standards, and a map of Eileen's own design). Eileen's own design is described in [BUILD.md](../BUILD.md) and is not repeated here.

## How to read this

- **[primary]**: a vendor documentation page, help article, changelog or the vendor's own repository, linked beside the claim and read on 2026-10-22 unless a date says otherwise. A few were re-read on 2026-10-25 while writing D77.
- **[ran]**: a probe run on 2026-10-22 against the unmodified `claude` CLI 2.1.304 on the owner's PC (model alias `haiku`, scratch folders only, a reduced environment, no credential file read).
- **[source]**: the open-source `openai/codex` repository, read at `main` and re-checked at tag `rust-v0.163.0` (released 2026-10-15).
- **[secondary]**: press or a third-party page.
- **[inferred]**: our reasoning from the sources.
- **[unverified]**: needs a test before anything depends on it.

## 1. The answer in brief

1. **The claude CLI already keeps the notes the owner described.** Its auto memory has Claude save `user`, `feedback`, `project` and `reference` notes as plain Markdown, loads the first 200 lines or 25 KB of a `MEMORY.md` index into every session, and reads topic files when needed ([memory](https://code.claude.com/docs/en/memory#auto-memory)) [primary]. These are the same four kinds Eileen's user model borrowed (BUILD 2.10 item 11), so moving the person to Claude's own notes changes where the text lives, not the shape of the data [inferred].
2. **Eileen turns it off today, and the reason it did so has a native answer.** Every session runs with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (BUILD 2.3 and 2.5) so that nothing learned would hide under the user's own Claude folder. The folder can be pinned per session with `autoMemoryDirectory` from the `--settings` file ([settings reference](https://code.claude.com/docs/en/settings-reference#automemorydirectory)) [primary], which works under Eileen's `--setting-sources ""` [ran]. So the notes can live in Eileen's data directory, inside its forget and canary rules.
3. **Not every session should keep notes natively.** The CLI has memory paths besides the model's visible `Write` and `Edit` calls: its changelog speaks of memory that is "recalled, indexed, or used by memory extraction" ([changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md), 2.1.273) [primary]. Whether those run in a `-p` session, and whether they pass Eileen's `PreToolUse` guard, is [unverified]. Sessions whose context always holds untrusted text (the brain, web and screen workers, the librarian) should therefore read the notes without writing them until a probe settles it [inferred].
4. **Every other route with a native memory also keeps it on the PC, each in its own silo.** Codex Memories live under `~/.codex/memories` and are off by default ([Codex memories](https://learn.chatgpt.com/docs/customization/memories.md)) [primary]. Grok Build keeps `~/.grok/memory`, experimental and off by default ([Grok memory guide](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/13-memory.md)) [primary]. No vendor reads another vendor's learned notes [primary, by absence in each vendor's docs].
5. **DeepSeek and local models have no memory of their own.** The DeepSeek API keeps no context ([multi-round chat](https://api-docs.deepseek.com/guides/multi_round_chat)) [primary], and Ollama's chat API takes the whole history on every request ([chat API](https://docs.ollama.com/api/chat)) [primary]. Both get memory only through a harness that has one, which for DeepSeek is the claude CLI Eileen already plans to point at DeepSeek's endpoint.
6. **The vendors' cloud memories cannot be reached from their CLIs.** Claude's app memory, ChatGPT memory and the Grok app's memory live on the vendors' servers, and none has a documented route into the vendor's own CLI (section 2.5, section 3 item 6 and section 4 item 4). So the local-first recommendation put to the owner costs almost nothing: the only vendor memory an Eileen session could use is already on the PC [inferred].
7. **Some things no vendor provides.** No vendor memory answers with no model, replays checked steps, keeps permissions, sees Eileen's tool calls and the user's reactions to them, or enforces one set of review, taint and forget rules across routes. Those stay Eileen's (section 8).

## 2. Claude, the v0.1 route

### 2.1 Auto memory

- **What it saves.** "As it works, Claude saves four kinds of notes for itself", recording the kind "as a `type` field in the memory file's frontmatter" ([memory](https://code.claude.com/docs/en/memory#auto-memory)) [primary]. It skips what the code or CLAUDE.md already says, and does not save something every session (same page) [primary].
- **Where.** By default `~/.claude/projects/<project>/memory/`, where `<project>` "is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory. Outside a git repo, the project root is used instead." "Auto memory is machine-local" and its files "are not shared across machines or cloud environments" ([memory, storage location](https://code.claude.com/docs/en/memory#storage-location)) [primary]. The docs' own summary row gives its scope as "Per repository, shared across worktrees" (same page) [primary].
- **Loading.** The first 200 lines or 25 KB of `MEMORY.md` load at the start of every conversation; topic files are read on demand. A write that leaves the index over a limit still succeeds, but the CLI "returns an error telling Claude to rewrite the index" (same page) [primary]. Auto memory is loaded "into the system prompt at session start" whatever the setting sources say ([Agent SDK features](https://code.claude.com/docs/en/agent-sdk/claude-code-features#what-settingsources-does-not-control)) [primary].
- **How notes are written.** "The agent writes new memories there with the standard `Write` and `Edit` tools rather than a dedicated memory tool" (same page) [primary]. A `-p` worker asked to remember a preference read `MEMORY.md`, wrote a topic file and edited the index, all as ordinary `tool_use` events in the stream [ran]. A preference mentioned in passing in a one-shot turn was acknowledged but not saved, in one sample [ran].
- **Note format.** On 2.1.304 a new note carried `name`, `description` and, nested under `metadata`, `type`, `originSessionId` and `modified`; older notes on the same PC carry a top-level `type` [ran]. The format is not a documented contract [inferred], so a reader must accept both and a nightly check should watch it.
- **What a warm session sees later.** The CLI records the system prompt on a conversation's first request and reuses it until compaction ([CLI reference, resumed conversations](https://code.claude.com/docs/en/cli-reference#system-prompt-flags-in-resumed-conversations)) [primary]. So a warm session probably does not see notes written after it started until it compacts or restarts [inferred, unverified]. After compaction, auto memory is re-read from disk ([context window](https://code.claude.com/docs/en/context-window)) [primary]. `--system-prompt-snapshot off` rebuilds the prompt on every request (same CLI reference page) [primary]; whether that also re-reads an appended prompt file is [unverified].
- **Off switches.** `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` disables it, and `=0` forces it on "even when `--bare` mode or `autoMemoryEnabled: false` would otherwise disable it" ([env vars](https://code.claude.com/docs/en/env-vars)) [primary]. `--setting-sources ""` does not turn it off [ran].
- **`--restricted` turns it off completely.** With `--restricted` the init event showed no memory path, a seeded index entry was not seen, and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=0` did not bring it back [ran, one probe]. The flag's documentation does not mention memory ([CLI reference](https://code.claude.com/docs/en/cli-reference)) [primary, by absence]. This collides with D40, which makes `--restricted` a second fence for every session if WP3's test shows workers still work under it.
- **Defence the CLI already applies.** Since 2.1.284, invisible characters and tags that imitate the CLI's own markup are neutralised in `MEMORY.md` and recalled notes before Claude sees them ([changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md), 2.1.284) [primary].
- **Context, not enforcement.** CLAUDE.md and auto memory are treated "as context, not enforced configuration"; to block an action, the docs point to a `PreToolUse` hook ([memory](https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory)) [primary]. A note can therefore never be a permission, which matches Eileen's rule that learned data never skips a confirmation.

### 2.2 Pinning the folder

`autoMemoryDirectory` takes "an absolute or `~/`-prefixed directory path" and is read from any settings scope, `--settings` included; from `--settings` it needs no workspace trust ([settings reference](https://code.claude.com/docs/en/settings-reference#automemorydirectory), [memory](https://code.claude.com/docs/en/memory#storage-location)) [primary]. The probes on 2.1.304:

| Probe | Result |
|---|---|
| Two sessions in unrelated folders, both with `--setting-sources ""` and the same `autoMemoryDirectory` in `--settings` | Both init events reported the same memory path [ran] |
| A main checkout, then a linked worktree created in an unrelated folder (as Eileen's job worktrees are) | Both mapped to the main checkout's memory folder [ran] |
| Two non-git folders shaped like Eileen's `run\<session>\cwd` | Two different memory folders [ran], so without a pinned folder every non-coding session would start empty [inferred] |
| A seeded index line, with a full custom `--system-prompt` and `--tools ""` | The session saw it [ran], so even a tool-less session can read the index natively |

If the setting is not honoured (a parse error, a CLI change, a session started without the file), the CLI falls back to the per-repository folder under the user's own Claude folder [primary, the storage rule above], which the owner's own sessions in that repository also load [inferred]. A session's init event reports its memory path [ran], so Eileen can check it before binding a job.

### 2.3 Side paths: recall and extraction

The changelog names memory work that is not a visible tool call:

- 2.1.77: a fix for "a race between memory-extraction writes and the main transcript" [primary].
- 2.1.273: a repository-chosen memory directory "is no longer loaded into the prompt, recalled, indexed, or used by memory extraction" when reads outside the working folders are blocked [primary].
- 2.1.284: markup neutralised in "recalled memory notes" [primary].
- 2.1.288: a fix for "memory recall" failing behind gateways that reject structured outputs [primary], so recall is a side model call [inferred].

No documentation page describes when extraction runs or whether a `-p` stream-json session runs it [unverified]. If it does, it could write notes from text the session read with no `Write` call for the guard to see, and recall could bring topic notes into context with no `Read` [inferred]. That is the main reason D77 gates native note writing on a probe and keeps memory off for sessions whose context is always untrusted.

### 2.4 Instruction files and setting sources

- Levels: managed policy, the user's `~/.claude/CLAUDE.md` and `~/.claude/rules/`, project `CLAUDE.md`, local `CLAUDE.local.md`; `AGENTS.md` is read in place of CLAUDE.md when none exists, from 2.1.277 ([memory](https://code.claude.com/docs/en/memory#agents-md)) [primary].
- Setting sources gate them: `"user"` loads the user's `settings.json`, CLAUDE.md, rules, skills, commands and subagents together ([Agent SDK features](https://code.claude.com/docs/en/agent-sdk/claude-code-features#control-filesystem-settings-with-settingsources)) [primary]. Eileen's `--setting-sources ""` therefore drops the owner's instruction files, and turning `user` back on would also bring the owner's allow rules and hooks into workers [inferred].
- `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` loads `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` and `CLAUDE.local.md` from `--add-dir` folders ([env vars](https://code.claude.com/docs/en/env-vars)) [primary]. That is a way to give a coding worker a repository's own instructions without the project setting source and its allow rules [inferred]; whether it applies when the folder is also the working folder is [unverified].
- The `InstructionsLoaded` hook reports each instruction file that loads, with its scope and reason ([hooks](https://code.claude.com/docs/en/hooks#instructionsloaded)) [primary]. It does not report auto memory recalls [inferred from the same page].

### 2.5 The Claude apps' memory (cloud)

The app memory saves "work and personal context" as topics, applies to "chats on the web, Claude Desktop, and Claude Mobile" and to Cowork when it runs in the cloud, is stored on Anthropic's side, and is managed in Settings > Memory (view, edit, delete, pause, reset) ([how memory works](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work)) [primary]. Import and export are experimental: the user pastes text into "Start import", or views memory or asks Claude to write its memories out ([import and export](https://support.claude.com/en/articles/12123587-import-and-export-your-memory-from-claude)) [primary]. Neither article, nor the CLI's memory page, describes a route from a CLI session to app memory [primary, by absence], so the only bridge is that manual text [inferred]. Skills enabled on the claude.ai account sync into terminal sessions signed in with that account, and are skipped when the setting sources leave out `user` ([skills](https://code.claude.com/docs/en/skills#where-synced-skills-load)) [primary].

## 3. OpenAI: Codex Memories and ChatGPT memory (after v0.1)

1. **Codex Memories.** Eligible past chats become Markdown under `~/.codex/memories/`, off by default ([Codex memories](https://learn.chatgpt.com/docs/customization/memories.md)) [primary], and off by default in the EEA, the UK and Switzerland since 2026-06-16 ([changelog](https://learn.chatgpt.com/docs/changelog)) [primary]. Consolidation writes `memory_summary.md` with User Profile, User preferences and General Tips sections, a `MEMORY.md` registry of task blocks (each with a "Failures and how to do differently" section), and `skills/` it writes itself ([consolidation prompt](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/consolidation.md)) [source].
2. **When notes are made.** A chat must sit idle six hours by default, and work runs only when a root session starts; generation spends plan quota and pauses below 25 percent remaining ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference.md)) [primary]. app-server threads count as memory sources because app-server tags its sessions with an eligible source, while `codex exec` runs do not ([rollout sources](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/rollout/src/lib.rs)) [source]. Developer-role messages are kept out of memory input ([rollout policy](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/rollout/src/policy.rs)) [source].
3. **Controls for an orchestrator.** `thread/memoryMode/set`, `memory/status` and `memory/reset` are experimental app-server methods in v0.163.0, and `thread/start` takes `ephemeral` and a `config` override map ([protocol](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/app-server-protocol/src/protocol/common.rs)) [source]. "Chat-level choices don't change your global memory settings" ([Codex memories](https://learn.chatgpt.com/docs/customization/memories.md)) [primary]. `memories.disable_on_external_context` keeps chats that used MCP, web search or tool search out of generation ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference.md)) [primary].
4. **Receipts.** Answers that used memory carry a `MemoryCitation` with file paths, line ranges and thread ids ([MemoryCitation](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/MemoryCitation.ts)) [source].
5. **Forget.** Only a whole-store reset and per-chat opt-out are documented; in the desktop app the reset "also clears Computer History when that feature is available" ([Codex memories](https://learn.chatgpt.com/docs/customization/memories.md)) [primary]. The code routes an explicit forget request into an ad-hoc note that consolidation applies ([read-path v2](https://github.com/openai/codex/blob/main/codex-rs/ext/memories/templates/memories/read_path_v2.md)) [source]; whether the released build exposes that path is [unverified]. OpenAI asks users to treat memories as "a helpful recall layer" and not to store secrets in them (same docs page) [primary].
6. **ChatGPT memory** is server-side: "ChatGPT web uses ChatGPT memory, while local Codex clients use a separate local memory store and controls" ([Codex memories](https://learn.chatgpt.com/docs/customization/memories.md)) [primary]. Deletion from OpenAI systems is scheduled within 30 days, and logs of deleted saved memories may be kept up to 30 days ([Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)) [primary]. No API reads or writes it [primary, by absence in the API docs index].
7. **Other native strengths for the slot.** `developerInstructions` and `baseInstructions` per thread; `skills/extraRoots/set` for extra skill roots per app-server process ([handler](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/request_processors/catalog_processor.rs)) [source]; thread resume, fork, archive, delete and compaction, `review/start` ([app-server](https://learn.chatgpt.com/docs/app-server.md)) [primary]; the Windows sandbox, which needs no admin setup on build 26200.9278 or later ([Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox.md)) [primary; Windows Home unverified]; `approvals_reviewer` should stay `user`, because auto-review approves "without a person" ([auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review.md)) [primary]. Codex's importer copies Claude project memories into Codex, behind a flag still under development in v0.163.0 ([import](https://learn.chatgpt.com/docs/import.md); [feature flags](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/features/src/lib.rs)) [primary, source]. Computer History is macOS only ([Computer History](https://learn.chatgpt.com/docs/customization/computer-history.md)) [primary].

## 4. xAI: Grok Build and the Grok app (after v0.1)

All from the [memory guide](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/13-memory.md) [primary] unless marked.

1. **Memory.** Experimental and off by default; `GROK_MEMORY=1` or `0` switches it per process, and "a managed remote setting" can also switch it on, so Eileen should always set it explicitly [inferred]. Notes live in `~/.grok/memory` (or `~/.grok/memory-v2`), are injected on the first turn and searched by `memory_search` and `memory_get`. `/remember` writes only after a review; "forget" is best-effort, and the guide says to edit the files for guaranteed removal or run `grok memory clear`.
2. **Per-session rules.** `--rules`, or `_meta.rules` on ACP `session/new` ([agent mode](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/15-agent-mode.md)) [primary].
3. **The Claude compatibility layer.** `[compat.claude]` switches, all on by default, make Grok read the user's `~/.claude` instruction files, rules, skills, the MCP servers in `~/.claude.json` and the hooks in `~/.claude/settings.json` ([configuration](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/05-configuration.md)) [primary]. Anything Eileen wrote at Claude's user scope would therefore also run in Grok sessions [inferred], and a Grok child started without those switches turned off would load the owner's personal MCP servers and hooks [inferred]. Whether capture can be turned off per process (`memory_v2.capture_enabled`) is [unverified].
4. **The Grok app's memory** is on xAI's servers and known here only from the press ([TechCrunch](https://techcrunch.com/2025/04/16/xai-adds-a-memory-feature-to-grok/)) [secondary]; nothing in Grok Build reaches it [primary, by absence].

## 5. DeepSeek and local models (after v0.1)

- **DeepSeek.** The API keeps no state ([multi-round chat](https://api-docs.deepseek.com/guides/multi_round_chat)) [primary]. Its automatic prefix cache is best-effort ([context caching](https://api-docs.deepseek.com/guides/kv_cache)) [primary] and about fifty times cheaper on a hit: $0.006 against $0.30 per million input tokens at peak for `deepseek-flash` ([pricing](https://api-docs.deepseek.com/quick_start/pricing)) [primary]. So notes and any person view should sit at the very start of the prompt and change in batches [inferred]. On Eileen's planned route (the claude CLI on DeepSeek's Anthropic-compatible endpoint with its own config directory), memory comes from the CLI's auto memory. DeepSeek's own harness, `dsh`, reads `~/.agents/AGENTS.md` and `~/.agents/skills` and is in developer preview ([agent instructions](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/context/agent-instructions/README.md)) [primary]; Windows support is not documented [unverified].
- **Ollama.** No memory ([chat API](https://docs.ollama.com/api/chat)) [primary]. `ollama launch` runs an official harness on local models ([CLI](https://docs.ollama.com/cli)) [primary], and Ollama also "offers a cloud service with hosted models" under `:cloud` tags ([launch post](https://ollama.com/blog/launch)) [primary], so a "local" route is local only when the endpoint is loopback and the model is not a cloud tag [inferred]. Whether `ollama launch` edits the harness's own settings is not documented [unverified].

## 6. Shared standards

- **AGENTS.md** is a shared format, not a shared place: it is project-scoped ("The closest AGENTS.md to the edited file wins", [agents.md](https://agents.md/)) [primary], and each harness reads a different user-level file (the claude CLI `~/.claude/CLAUDE.md` and rules; Codex `~/.codex/AGENTS.md`; Grok `~/.grok/rules/` and the Claude files; `dsh` `~/.agents/AGENTS.md`) [primary, each vendor's docs above]. So one person file must reach each route through that route's own per-session channel [inferred].
- **Agent Skills** (`SKILL.md`) are read by the claude CLI, Codex, Grok Build and `dsh` ([agentskills.io](https://agentskills.io/); each vendor's docs) [primary]. The claude CLI does not read `~/.agents/skills` (a request was closed as not planned, [issue 56193](https://github.com/anthropics/claude-code/issues/56193)) [primary].
- **MCP memory servers.** The reference server keeps entities and observations in one JSONL file and lets several clients share it ([server-memory](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)) [primary]. It is a second store that a model writes to silently unless fronted [inferred], so it is at most a later option.
- **Third-party memory layers** (mem0, Basic Memory, Graphiti and others) would be the parallel user model the owner turned down; some need model API keys, and Basic Memory is AGPL-3.0 ([Basic Memory](https://github.com/basicmachines-co/basic-memory)) [primary].
- **Portability by summary.** The vendors' own bridge between assistants is a pasted text summary: Claude's import and export, and Gemini's import ([import and export](https://support.claude.com/en/articles/12123587-import-and-export-your-memory-from-claude); [Gemini Apps Help](https://support.google.com/gemini/answer/16868299)) [primary]. Google says imported chats are used "to improve our services" (same Gemini page) [primary]; Gemini is not an Eileen route.

## 7. The open point: local first, cloud opt-in

**Recommendation, put to the owner and applied until he says otherwise.** Use only vendor-native memory stored on the PC: the claude CLI's notes in Eileen's data directory, later Codex's `~/.codex/memories` and Grok's `~/.grok/memory`. It matches OWNER-DIRECTION 2026-10-20 ("keeping all of this on the user's PC, private by default") and BUILD 2.12 ("Everything stays on the PC except what a Claude session sends to the owner's own plan"). Cloud-side memories are opt-in per route, and the only path is each vendor's own manual bridge: the owner pastes what an app remembers, Eileen shows each line as untrusted text, and a line becomes a note only after a yes. Eileen never signs in to a vendor app or drives one to read memory, because that would turn screen text into stored data [inferred].

**What local first costs.** Almost nothing, because none of the CLIs can read its app's memory (section 2.5, section 3 item 6 and section 4 item 4).

**The alternative.** Treat cloud memories as first-class sources: copy claude.ai synced skills into sessions, allow Codex cloud tasks, and remind the owner each month to paste what each app remembers. The costs: "what do you know about me" and "forget that" become incomplete (ChatGPT keeps deletion logs up to 30 days, section 3 item 6), more personal data sits on vendor servers, the "on the user's PC" line in OWNER-DIRECTION would need the owner's own amendment, and the CLIs still could not read app memory, so it adds little.

## 8. What the design must answer, and what stays Eileen's

**Risks, from the sources above** [inferred unless marked]:

- **Memory poisoning.** A note written from injected text persists into later sessions; Anthropic warns of this for read-write memory stores ([Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory)) [primary]. A coding job counts as untainted while it reads its own repository, so a README or a dependency's source could ask the model to save a note.
- **Side paths.** Extraction and recall may bypass the guard and the receipts (section 2.3).
- **Leaks.** Web-reading workers that hold the whole notes index could be told by a page to send it somewhere.
- **Copies.** Note text also lands in trajectories, hook bodies, recordings, the CLI's file-history snapshots and freed disk space, which a forget must reach or name.
- **Scattering and fallback.** Without a pinned folder, notes scatter; if the pin fails, they land where the owner's own sessions load them (section 2.2).
- **Concurrency.** Several sessions and Eileen's own writer may edit one `MEMORY.md`; the CLI refuses an edit of a file changed since it was read, and has had write-conflict bugs ([changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md), 2.1.280) [primary].

**What stays Eileen's, because no vendor provides it:** the model-free fast path (L1 grammar, fact phrases, phrasings, slot aliases, induced templates, the L2 matcher); typed recipes with checks, replay, shadow agreement, the ladder, the linter and computed provenance; dictation vocabulary for the local recognizer; source statistics and the answers cache; the episodic desktop ledger (Codex's equivalent is macOS only, section 3 item 7); voice profiles and consent records; settings, persona and permission grants (a grant must never live where a model writes, section 2.1); trajectories, regret signals, step corrections and receipts; and the cross-route rules and the parts that enforce them (the writer with no model, the notes guard, taint and provenance, the forget plan).

## 9. To test before anything depends on it

1. Does memory extraction run in a `-p` stream-json session, when, and does it write when `--tools` lacks `Write`? Do its writes fire `PreToolUse` and obey a deny? Is recall visible in the stream, and what does it add to the brain's time to first text with a 200-line index? Which files does the CLI create in `autoMemoryDirectory`? Can extraction or recall be turned off alone?
2. Under `--permission-mode dontAsk`, can a worker write into a pinned `autoMemoryDirectory` outside its working folders, or does it need `--add-dir`?
3. Does `CLAUDE_CODE_DISABLE_AUTO_MEMORY=0` with `--add-dir <memory folder>` bring memory back under `--restricted` (the one probe said no without `--add-dir`)?
4. Does a warm session see notes another session wrote after it started? Does `--system-prompt-snapshot off` re-read an appended prompt file?
5. Does the CLI write file-history snapshots under `-p` with `--no-session-persistence`, and does `CLAUDE_CODE_DISABLE_FILE_CHECKPOINTING=1` stop them?
6. Does `--add-dir` with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` load a repository's CLAUDE.md (or AGENTS.md) when that folder is also the working folder?
7. Can native compaction be triggered in a warm stream-json session, and how long does it take against a recycle?
8. Does the claude CLI have a native consolidation pass for auto memory? A skill named for consolidating memory exists in the desktop environment this research ran in, but no CLI documentation was found.
9. Codex, once installed: do app-server threads produce memories and `exec` runs not; is Memories available on the owner's plan; does a per-thread memory override take effect; does `thread/memoryMode/set disabled` after a turn keep that thread out of extraction?
10. Grok: per-process capture control, whether `GROK_HOME` moves the sign-in, and a flag that stops a session from being saved.
